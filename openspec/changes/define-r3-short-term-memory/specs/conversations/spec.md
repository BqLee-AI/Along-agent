## MODIFIED Requirements

### Requirement: 常驻输入与连续会话

系统 SHALL 在首次发送、运行中和运行结束后保留可达的对话输入面；完成后可在同一会话明确发送下一轮。连续消息来自已存可见消息与原运行事件，不凭文本相似度猜测关联或重复拼接最终档案与同一流式回复。采用新合同的新 Harness Run 接纳时冻结完整当前输入及同用户、同会话可用上下文与来源，不再以固定 63 条或对应消息引用上限裁剪；实际模型视图可以使用有来源摘要，但原始消息和冻结事实不改写，容量、模型窗口、输出及预算门仍生效。旧 Run 和其批准恢复保持原冻结引用与策略，不补造历史上下文、不混入后来消息、不重放旧工具调用。见 [design/23](../../../../../docs/design/23-r3-short-term-memory-and-compact.md)。

#### Scenario: 不选工具的多轮交流（D8/D10）

- **WHEN** 用户直接发送普通问题，收到回复后在原页面追问
- **THEN** 输入不消失，页面保留前轮消息与本轮回复；第二轮沿原 conversation_id 新建 Run，使用接纳时冻结的同用户同会话上下文及完整当前输入，不混入其他用户、其他会话的原始消息或 system 消息；合法的 owner 记忆按独立记忆合同使用

#### Scenario: 刷新后明确追问（D8/D9）

- **WHEN** 用户刷新、重登或从历史发现原会话，再输入下一条消息
- **THEN** 加载和历史恢复只有 GET；输入面仍可达，只有用户明确发送才创建新 Run，新运行使用同会话已存可见上下文，不重发旧消息或自动恢复旧执行

#### Scenario: 在途和未知状态保留边界（D8/D9）

- **WHEN** 原运行仍在执行、等待批准、发送结果待核实或工具效果未知
- **THEN** 输入面继续展示真实不可发送原因，不能通过发送新消息绕过原运行；继续和取消仍走原 Run 的明确操作，不把输入新文本当成批准或恢复

#### Scenario: 有界窗口与批准恢复（D5/D8/D9）

- **WHEN** 会话历史超过 64 条消息，或原批准等待后又出现后来消息
- **THEN** 新合同 Run 不因 63 条和相应引用上限丢弃更早历史；实际装配必须满足容量门，不截断当前输入或伪报成功；原批准恢复沿原冻结引用、不混入后来消息，旧 Run 不补造上下文，容量不足明确失败、不切换模型

## ADDED Requirements

### Requirement: 手动和自动对话 compact

会话 SHALL 提供显式手动 `/compact`，并允许按可信容量条件自动触发；两种入口共用运行时摘要与来源、并发及失败合同。摘要不替代原始可见历史，历史读取仍只读；不将指令文本当作普通对话发送或批准。见 [design/23](../../../../../docs/design/23-r3-short-term-memory-and-compact.md)。

#### Scenario: 运行中与空闲会话手动 compact

- **WHEN** 用户对运行中的会话发出 `/compact`，或对无活动 Run 的空闲会话发出该命令
- **THEN** 运行中先独立通用暂停、等待合法安全点，摘要后按同 Run 继续规则裁决；空闲时由用户明确接纳真实 compact 控制 Run，使用其独立预算和初始安全点，针对该会话可验证的已存范围执行同一摘要流程，不伪造既有任务 Run、批准等待或工具结果；两者都如实呈现成功或失败

#### Scenario: 自动触发与历史保留

- **WHEN** 合法自动条件成立，或用户随后刷新、查看历史
- **THEN** 触发在当前模型流结束且下一请求前的安全点进行，已有原文和原回复按原合同可读，不把摘要当原话，不因 GET 重新摘要或自动恢复执行

#### Scenario: 提交与新消息竞争

- **WHEN** compact 生成期间会话出现新消息或取消先于摘要提交
- **THEN** 原子验证覆盖边界和状态，后来的消息不被摘要掩盖、删除或当作已覆盖；取消先赢时不发布摘要，历史及真实部分结果保持原样
