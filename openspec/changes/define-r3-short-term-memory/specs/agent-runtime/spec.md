## MODIFIED Requirements

### Requirement: 执行上下文与事件补读分离

系统 SHALL 将有限等待快照与对外事件投影分开。快照只追加、仅引用已接受且受当前 owner/Run 校验的调用，预算及逻辑调用进度不倒退；事件补读不启动执行。非事务 unknown 正常失败，不构造可恢复的未知快照。外部事件和冻结展示仍遵循原合同。新合同增加独立通用安全点，仅其明确合法的暂停点或原有效批准等待点可按各自规则继续；旧 Run 不因此取得新恢复资格。见 [design/23](../../../../../docs/design/23-r3-short-term-memory-and-compact.md)。

#### Scenario: I4 GET 或入站幂等补读

- **WHEN** GET after_seq 补读，或同入站键重放已挂起/终结 Run
- **THEN** 只返回已存对外事件，不启动进程、新建 attempt 或再次调用工具；running 仍遵守既有冲突规则

#### Scenario: I4 内部快照与旧事件

- **WHEN** 新内部快照和对外事件交错持久化，或读取历史业务 Run
- **THEN** 内部快照不交给外部 ThreadEvent 解析，游标间隙不导致漏帧；历史事件原样可读，不能伪造可恢复上下文

#### Scenario: I4 非法恢复点

- **WHEN** 调用者提交他人、过期等待点、普通中间 checkpoint、已取消或终态 Run 的恢复请求
- **THEN** 不启动新 attempt、不重放工具；新合同仅允许各自有效的批准等待点和通用安全暂停点，旧 Run 仍限原有效批准等待点

#### Scenario: R1 未知效果正常终结（D8/D10）

- **WHEN** 正式文件工具返回没有已接受结果的 unknown
- **THEN** native 正常失败并保留真实未知调用，不将其加入恢复快照或继续模型/工具；GET 只读，终态恢复被拒绝

### Requirement: 有界批准恢复与不可变上下文策略

系统 SHALL 使用冻结的 per-Run policy 和完整 snapshot2 引用重建有界 start；批准恢复只使用显式有效批准等待点，不扩大旧 Run 权限。新合同的独立通用暂停遵循自身安全点合同；不改变旧 Run 或批准恢复的冻结输入、权限、预算和决议。见 `docs/design/18-r2a-harness-context.md` §3、§6、§8 与 [design/23](../../../../../docs/design/23-r3-short-term-memory-and-compact.md)。

#### Scenario: 批准后大观察恢复（D6/D8）

- **WHEN** 用户批准后显式继续，原全量观察聚合超过 1MiB
- **THEN** 先核当前决议/权限，再用全部引用的有界视图启动唯一新 attempt，不先拼超限全文、不重跑 MCP；拒绝/未知与原 apply 身份仍不绕过

#### Scenario: 旧 Run 及策略并发（D8/D9）

- **WHEN** 旧有效等待点在新执行器恢复，或部署策略后来变化/并发恢复
- **THEN** 原冻结输入/预算/allowlist 不变，策略最多补入一次且同恢复事务原子；无新增回取资格时保留唯一正文，放不下明确失败，不自动扩权

#### Scenario: 只读与取消（D1/D8/D9）

- **WHEN** GET/同入站键补读，或旧 pipe/取消后提交内部源查询、测量后的模型请求
- **THEN** 只读不创建策略或 attempt，不执行；旧或取消资格拒绝新读取/动作，不披露被撤权内容，不覆盖既成事实

## ADDED Requirements

### Requirement: 通用安全暂停与同 Run 继续

新合同的 Run SHALL 支持与批准等待独立、可独立使用的通用暂停及同 Run 继续，而非 compact 的私有状态；该能力是进行中手动和自动 compact 的前置。只有已完成当前模型流、工具结果已按真实接受状态裁决且可冻结一致执行上下文的安全点可提交暂停。批准等待不被伪造成通用暂停，也不使用虚构批准实现暂停；此合同不承诺任意崩溃恢复。见 [design/23](../../../../../docs/design/23-r3-short-term-memory-and-compact.md)。

#### Scenario: 不依赖 compact 的暂停和继续

- **WHEN** 本人显式暂停支持新合同的活动 Run，稍后在合法安全点显式继续，且无需执行 compact
- **THEN** 使用独立通用暂停点和同 Run 的唯一继续资格，不创建批准、不要求摘要或记忆、不重置预算；普通 checkpoint 或进程崩溃不因此取得恢复资格

#### Scenario: 模型流和工具边界

- **WHEN** 运行中请求暂停，模型仍在流式响应或工具尚未裁决
- **THEN** 不在流中插入摘要或恢复点；等流结束和工具已接受结果进入真实账后才可在安全点暂停，已接受动作不重放；unknown 按原失败合同停止，不伪造安全点或当作未发生

#### Scenario: 取消及并发继续

- **WHEN** 暂停、继续、完成和取消竞争，或同一暂停点被并发/重复继续
- **THEN** 以原子裁决产生唯一合法状态，同一暂停点最多一个有效继续 attempt；取消先提交不允许后续模型、工具、摘要提交或成功覆盖 cancelled，已接受效果仍如实保留

#### Scenario: 继续的权限与预算

- **WHEN** 暂停后显式继续，权限已撤销或预算/容量不足
- **THEN** 按当前资格拒绝新动作或如实报告预算/容量失败，不扩大冻结权限、不重置跨 attempt 预算、不新建替代 Run；旧 Run 和原批准恢复不混入新消息

### Requirement: 手动和自动 compact 共用有来源摘要

系统 SHALL 在合法安全点让手动 `/compact` 与自动触发复用同一摘要能力；摘要输入和输出隔离于 system 指令及业务工具权限之外，引用可信 owner/会话来源和明确覆盖边界，作为可校验的派生上下文，不覆盖原始消息、工具结果、批准或冻结事实。自动触发不得假设未知窗口或不可计量输入的百分比；模型调用占用同 Run 累计预算，可得 usage 如实记录，缺失保持 unknown。

#### Scenario: 来源、并发和取消

- **WHEN** 摘要生成中发生新消息、另一 compact 或取消
- **THEN** 提交须校验同 owner、覆盖边界与当前状态并原子裁决，不覆盖边界之后的消息、不重复覆盖已提交范围；取消先赢时不发布摘要或记忆，原文与已接受事实仍可读

#### Scenario: 失败与容量

- **WHEN** 摘要请求失败、协议错误、输出截断/无效、来源不匹配或容量/预算不足
- **THEN** 不发布部分摘要或候选为成功，不删除原文或冻结事实；报告真实失败及可得 usage，未知不伪造为零，不静默切换模型或无限重试；继续资格依据真实运行状态而非假设成功

#### Scenario: 摘要提交后记忆保存失败

- **WHEN** 摘要及其覆盖关系已合法提交，随后本次 compact 的记忆候选校验或保存失败
- **THEN** 不回滚或伪造摘要结果，不声称记忆保存成功；原消息仍可读，继续资格按真实状态、预算和权限裁决，取消先提交时不得接纳迟到候选
