## ADDED Requirements

### Requirement: 当前 Harness 提醒等待点的就地明确确认

系统 SHALL 允许用户在当前选中的 Harness 提醒批准等待点完整审阅冻结内容，再通过明确的“确认创建并继续”或“确认取消并继续”按钮授权这条提醒并继续原 Run。确认只使用所见原冻结正文与展示校验信息，不以摘要、聊天回复或 DOM 重建授权内容；一次点击不是免批准，也不授权文档或后继提议。沿用 design/09 §6、design/17 §5–§7 与既有批准/恢复 API，不新增执行事实或前端领域状态机。

#### Scenario: 完整审阅后明确创建或取消（D2/D5/D8）

- **WHEN** 当前选中 Harness Run 已挂起于提醒批准等待点，用户在桌面或约 375px 窄屏审阅提议
- **THEN** 原话、冻结时间与时区、完整冻结正文、有效期和通知边界可读，明确创建或取消按钮可由键盘操作；只有点击该按钮才提交对应原批准的确认，普通聊天肯定语不产生授权

#### Scenario: 已确认结果不冒充调度终态（D8/D10）

- **WHEN** 原提醒确认返回经核验的 consumed 决议与真实任务引用
- **THEN** 页面展示该任务的真实结果入口，不再显示这条已消费提议的待确认按钮；确认成功不等于已调度、已送达或已取得取消回执，运行终态和任务状态分别读取

#### Scenario: business 与文档路径不扩展（D5/D8）

- **WHEN** 用户从提醒快捷入口取得已完成的 business 提议，或审阅文档批准
- **THEN** business 继续使用既有独立提醒批准页，不虚构挂起 checkpoint 或继续；文档仍独立审阅与显式继续，提醒按钮不批准或执行文件修改，独立批准详情链接保留新标签页路径

### Requirement: 仅按原授权与等待点衔接恢复

系统 SHALL 在同一次仍有效的明确按钮动作内，核对原 conversation、Run、提醒批准与 checkpoint，且仅在确认 consumed 及真实任务引用后请求同 Run 的原等待点恢复。恢复仍服从服务端当前资格、原预算和唯一有效 attempt 合同；旧批准及迟到响应不能越过原等待点。沿用 agent-runtime 的批准等待与同一 Run 显式恢复要求及 design/09 §6。

#### Scenario: 确认后按原等待点继续（D8/D9）

- **WHEN** 用户明确确认当前 Harness 提醒，确认决议已核验且原等待点仍有效、服务端允许恢复
- **THEN** 同一次动作继续原 Run，绑定原批准和 checkpoint，不再要求正常成功路径额外切页或点击继续，不新建消息、Run、批准或重复执行原提案

#### Scenario: 等待点改变或动作失效（D8/D9）

- **WHEN** 确认前或衔接恢复前原 Run、批准或 checkpoint 已改变，或用户已经切换目标、离开或停止
- **THEN** 不以原按钮动作恢复另一等待点，不自动追随后继提议；保留可核实的已发生结果，读取最新事实，新的提议须重新完整审阅并明确授权

#### Scenario: 决议不可确认或当前不可继续（D5/D8/D10）

- **WHEN** 原提议已过期、拒绝、被替代、冻结内容不匹配，确认回执不可核验，或 Run 当前不可继续
- **THEN** 不在未核验 consumed 时衔接恢复，不猜测缺失结果或绕过服务端资格；已读授权事实仍保留，提供只读核对与有事实依据的反馈，不把 can_resume=false 一概解释为尚未批准

### Requirement: 失败重试与历史读取不重复授权

系统 SHALL 复用既有确认与恢复的独立幂等合同：确认使用原批准的稳定请求键与冻结内容，恢复使用原 checkpoint 的稳定恢复键；双击、未知回执和恢复失败不产生第二份业务效果。历史和读取不触发动作链，沿用 design/17 §6–§8 及身份恢复的只读要求。

#### Scenario: 双击与确认未知响应（D5/D8/D9）

- **WHEN** 用户快速重复点击，或确认响应丢失后再次明确请求核对原确认并继续
- **THEN** 在途动作互斥；未知结果先 GET 原批准，已 consumed 时复用真实任务而不再次 POST 确认，仍 pending 才允许原键与原冻结内容重试；读取失败不盲目重发、不换键建新任务

#### Scenario: 已确认但恢复失败（D8/D9）

- **WHEN** 确认已成功，而同 Run 恢复失败或响应未知
- **THEN** 保留真实已确认结果，先读取原 Run，再由用户明确重试原 checkpoint 的原恢复键；不重新确认、不发送新消息、不因重试分配第二个有效恢复 attempt

#### Scenario: 历史、刷新与重登不执行（D5/D8/D9）

- **WHEN** 用户读取静止历史、展开批准结果、刷新、回退、重登返回或恢复网络连接
- **THEN** 仅 GET 获取已存事实，不自动确认、恢复、取消或发送；已消费的旧批准不成为再次执行授权，文档与后继提议也不因本次读取或原提醒动作自动执行
