## MODIFIED Requirements

### Requirement: A4显式时区与Web候选重提议

系统 SHALL 按 `docs/design/05-time-core.md` §9.1/§9.2和conversations §2/§4的字段与优先级识别显式时区、保留结构化fold，并在Web用服务端候选完成新键重提议；客户端不得计算UTC或将选择当成确认。相对日期的锚归属与本地跨日判定按[本change设计](../../design.md) §3执行：同一请求不因仅经过60秒改义，新明确日期的新Run与可信前序请求澄清分别建锚或继承，不改变旧Run/重放/批准恢复冻结值。

#### Scenario: confirmed timezone不能吞未知别名

- WHEN 原文给未知显式别名/规范ID，分别在无已确认值及已有Shanghai默认值下提交
- THEN 均为UNKNOWN_TIMEZONE typed失败422，不静默忽略或排到Shanghai；多个不同有效时区则问清，不按别名表顺序选首项（映射A4、D1/D8）

#### Scenario: first与second保留同一意图

- WHEN 真实Web收到纽约歧义失败后用户分别选择第一次或第二次
- THEN 显示服务端偏移并保留原输入、明确日期/纽约时区与对应结构化fold_choice，用新幂等键重提议；服务端独立归一，2026-11-01 01:30得到对应05:30Z/-14400或06:30Z/-18000，pending回显冻结数字fold与偏移，只有按钮确认才建task（映射A4、D2/D8/D10）
- THEN 选定后的 SSE 正文与审批详情均明确第一次/第二次及对应数值 UTC 偏移；新 first 冻结 v2 并按同一版本计算 hash 和校验所见正文，不能以缺少选择语义或偏移的旧普通回显确认。既有 v1 模板不悄悄替换，有展示缺陷的旧提议作废后重来，正确的冻结新旧对象不依赖当前规则可用性（design/06 §2、§5，映射A4、D2/D8）

#### Scenario: 编辑或跨午夜不沿旧候选算UTC

- WHEN 用户编辑原日期/时区，或继承原请求锚的相对表达重提议已实际跨过确认时区本地午夜
- THEN 清除不再适用的候选选择并重新校验；真实跨日要求明确具体日期，保留原请求可追溯锚而不按点击时刻重算，不复用未选fold的幂等键、不用/me覆盖明确纽约、不从自由文字猜fold或由客户端算UTC（映射A4、D1/D2/D8）

#### Scenario: 同日本地澄清超过60秒不是跨日

- WHEN 同一提醒的可信澄清或重提议与其原请求锚处在同一已确认时区的相同本地日期，且仅接收间隔超过60秒
- THEN 不仅因该间隔返回DATE_CHANGED或重算相对日期，保留原明确锚并继续独立校验字段、规则覆盖和fold；缺日期使用DATE_MISSING说明缺字段，缺时区/时段/事项仍澄清且无批准（映射A4、D1/D2/D8/D10）

#### Scenario: 新日期请求与原候选重提议分离

- WHEN 旧会话接纳用户独立新说今天或明天的提醒，或Web在延续原未完成提醒时带回含相对词的原文及fold选择
- THEN 前者按本轮服务端接纳锚归一，后者仅在同一提醒关系与来源可信时保留原锚；多个候选、无关中间目标、缺来源或意图不明均先澄清，不取最新任意Run或会话初始锚，原文相对词不自动授权换锚（映射A4、D1/D2/D8/D10）

#### Scenario: 实际跨午夜与冻结恢复互不替代

- WHEN 可信原提醒的相对表达在确认时区从23:59:50到次日00:00:10以新键重提议，或原Run的消息/工具重放、批准恢复和历史读取发生在午夜之后
- THEN 新重提议即使仅间隔20秒仍问具体日期且无批准；重放、恢复与读取使用原冻结上下文和原结果，不因当前钟换日而重归一或改写UTC/fold/展示；重放或读取不新建Run、不重复执行已完成工具或创建批准与承诺，既有重放审计与合法批准恢复的attempt仍按各自合同记录，批准恢复继续执行原授权与有效期门（映射A4、D2/D6/D8/D9）
