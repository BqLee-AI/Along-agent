# 提醒日期锚：请求归属与冻结边界

## 1. 现状与必要性

Observed：采纳前基线 `61693cf` 将 `conversation.anchor_received_at_utc` 用于连续会话的新 Run，并将本地跨日或固定锚龄超限判为 `DATE_CHANGED`。纯入口使用显式 `anchorReceivedAtUtc`；`propose_task` 的时间原话与事项 `note` 分离，纯归一不拥有时钟、DB 或批准事务。此处记录旧行为原因，不作为采纳后的合同。

历史行为证据：中文时钟 Red 曾将“3点二十分”解析为15:00而非15:20，属于独立格式缺陷，已由 [#97](https://github.com/BqLee-AI/Along-agent/pull/97) 合并修复。日期 Red 显示新“今天”沿用旧会话日期、同日几分钟澄清被标为跨天；这些是历史观察，不代替新锚的精确实施快照验收。

合同采纳：[#98](https://github.com/BqLee-AI/Along-agent/pull/98) 已合并，#92 已授权按该 change 实施。以下 Required 合同取代 design/05 旧延迟重问和会话锚复用语义；原归档任务仅保留历史适用范围。主 spec 只在正式 archive 时归并，本次不改 proposal 或 spec 增量。

## 2. 候选取舍

| 候选                                             | 收益                                         | 代价/风险                                                      | 结论          |
| ------------------------------------------------ | -------------------------------------------- | -------------------------------------------------------------- | ------------- |
| 保持会话初始锚和锚龄重问，仅修话术               | 无日期行为迁移                               | 旧会话新明确日期仍不能按本轮自然理解；同日澄清仍需重述         | 不满足#92目标 |
| 每条新消息都换锚，或无日期就继承最后任意Run      | 改动小                                       | 跨午夜补时区会悄悄滚日；无关消息、多个提醒和旧缺元数据会误继承 | 拒绝          |
| 新明确日期用本轮接纳锚，可信同一提醒澄清继承原锚 | 新日期与原请求都保持来源；不把时钟经过当授权 | 必须验证提醒关系与冻结来源；不确定只能澄清                     | 已采纳        |

## 3. 采纳合同

Required：日期锚归属于被接纳的提醒请求，而不是整段会话的寿命。新用户明确说今天/明天/后天/昨天并形成新 Run 时，用该消息服务端接纳时刻建立本轮不可变日期上下文；明确绝对日期不从时钟补年份或改日。客户端时间仅诊断，模型只传原时间表达，不能生成权威锚或 UTC。

“新明确日期”指用户明确发起新的日期陈述，不是工具重放、按钮选择fold时携带的原文或服务器重放的旧消息。延续原提醒的候选重提议即使带回原文中的“今天/明天”，仍须证明同一提醒关系并保留原锚；不能仅靠相对词正则重置。若无法区分新请求与原澄清，必须先澄清意图；用户确认新的完整日期请求后，才按新的服务端接纳事实建锚，不能回填旧Run。

仅补时区等消息没有新的日期授权。继承须同 owner、同 conversation，并从**全部未完成候选中恰好找到一个**；该源 Run 须为 done/failed、对应紧邻上一 user 消息，原输入/冻结来源可追溯，实际接受结果为 `TIMEZONE_MISSING` 澄清或 `AMBIGUOUS_LOCAL_TIME` 候选失败。已被后继 `sourceRunId` 引用的源排除，不用“最新 Run”、文本相似或模型声称继续代替关系证明。多个候选、无关中间 user 目标、缺失/损坏来源或关系不明时，要求完整重述日期、时刻、时区和事项。当前消息不是批准或恢复入口。

支持的澄清只有整条明确时区别名/规范 ID 补原缺时区，以及精确 fold 重提议。后者必须以可选请求字段 `clarification_of_run_id` 明确引用原失败 Run，原文与原提醒完全相同、请求时区等于实际候选并提供 first/second；相对词原文被带回不构成新请求。其他自由文本补充不猜字段，要求完整重述。

继承只复制明确的原请求日期上下文进入新 Run，不修改前 Run；当前接纳时刻单独冻结用于跨日判断。同一确认时区内本地日期相同，等待时长本身不是跨日，不换算原相对表达；本地日期实际变化则要求具体日期，不将原“今天”解释为新一天。无确认时区先问，不用设备/位置猜本地日界。

例如同一确认时区内原接纳为本地11月1日10:00、可信澄清为10:02，保留原锚，不以120秒间隔报跨日；原接纳23:59:50、澄清11月2日00:00:10，即使仅20秒仍须问具体日期。独立新请求“今天下午提醒……”使用11月2日本轮接纳锚，不继承11月1日；未来时间和批准有效期仍独立校验，取消锚龄重问不放行过期目标。

同一 Run 内部工具调用、已预约调用重放、同键消息重放和批准恢复只消费其持久冻结的 anchor/received，不因等待或重启读取当前钟。既有规则覆盖、fold、偏移、UTC、presentation 和确认有效期不重算；新的显式日期陈述只能建立新请求，不能覆写旧对象。

## 4. 责任与兼容

- conversations 拥有消息接纳、原提醒关系验证与 Run 冻结。service 在接纳事务取 DB `clock_timestamp()`，新请求的 `anchorReceivedAtUtc` 和本轮 `receivedAtUtc` 同源；可信澄清的 anchor 复制原请求，received 仍用本轮接纳时刻。`conversations/reminder-date.ts` 验消息/Run/唯一未完成来源及紧邻关系；`tools/reminder-source.ts` 提供实际接受结果投影，不能跨模块从模型文本猜结果。
- 最小公开新增为可选 UUID `clarification_of_run_id`，fold 精确重提议必填；来源引用纳入原入站请求规范 hash 材料，提供时追加在原材料（及可选 workspace）之后，省略不追加以保持无引用旧 hash。同 owner/key 换来源引用为409，不新建 Run。它只是待核验关系，不是 owner/权限或时钟输入。
- 新 Run 在既有 `frozen_context` 写 `reminderDateSource={version:1,kind:new|clarification|unresolved,inputMessageId,sourceRunId?,sourceInvocationId?}`。new/unresolved 的 inputMessageId 为本轮消息；clarification 指权威原提醒消息，sourceRunId/sourceInvocationId 记录实际来源 Run 与已接受结果。`unresolved` 只允许要求完整重述，不授权新提醒；本轮 Run 的 `input_message_id` 仍指实际新消息。
- 复用 0015 对 `frozen_context` 的不可变约束；不新增列/表/迁移、不修改旧 Run 或回填来源。缺来源旧数据可以按原合同读取、重放与批准恢复，但不能成为新澄清的继承证据。
- 公共归一用例只接收显式不可变值；所有时区偏移、本地日期和跨日计算仍归 time-core 纯层，不读系统钟、env、网络或 DB，继续执行有限覆盖和字段完整性检查。
- gateway 保持 `raw_time_text` 与 `note` 分离，按当前 Run 持久来源核验日期表达等于权威原输入，raw_time_text 为原文子串，澄清 note 也为原文子串；不让历史模型上下文带回日期或改写事项。缺日期/时区/时段/事项只有澄清，无批准/承诺写入，模糊语法不猜。
- A2 revise 仍使用其持久首次接收锚；旧 Run 工具、读取、按钮确认、取消和 worker 沿原冻结值。新 Run 来源只用于该 Run 的后续消费，不在工具或恢复入口重新取钟；不扩展为通用会话状态机。

## 5. 验收与交付

采纳合同后同步 design/05 §0/§3/§5.2/§9.2、Agent 话术、黄金第14条、PRD、索引及 API/schema，消除会话日期锚和延迟语义冲突。实施、合同审阅和运行验收分别留证；主 spec 只在正式 archive 时归并增量。

D1/D2/D6/D8/D10 与 A4：旧会话新明确今天/明天用本轮接纳锚；可信整条时区补充保留原锚；关系不明、多个候选、无关中间 user 目标或旧缺来源不能猜；同日120秒与真实本地午夜20秒分别验收；缺时区先问，缺日期/时段/事项零批准。fold 必验显式来源引用、完全相同原文、实际候选时区/选择及来源 hash 冲突。A2/D2/D6/D9：同键重放、原 Run 工具、批准恢复和只读历史不重算、不重复执行或改写旧冻结；未来时间/有效期和确认门保持原合同。

纯函数/API/PG行为、正式native消费与真实模型质量分别报告。仅检查返回context不等于已证明真实工具提议、批准冻结或跨轮归一；不创建真实用户提醒，不要求用户凑对话，不沿用混合工作树历史Green冒充精确实施快照证明。
