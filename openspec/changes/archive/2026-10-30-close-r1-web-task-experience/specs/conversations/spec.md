## ADDED Requirements

### Requirement: 基于 LumenUI 的全站 Web 重构

系统 SHALL 使用自有 LumenUI（基于 shadcn/Base UI）作为统一组件基础并配合 Tailwind CSS，完整重构应用布局、导航、全部 Web 页面及交互组织，而非仅在旧 Demo 上优化样式或局部替换控件。范围包括今日、对话/历史/Run、提醒确认、文档批准、提醒任务/详情、活动及账户/登录/建号/转正/退出；旧布局和配色不构成约束。保留后端能力、身份/权限、公开深链和业务安全合同；最终移除已替换的旧 UI，不维护平行实现。方案见 design.md §1–§2、§4–§7。

#### Scenario: 全站一致的真实使用路径（D8/D10）

- **WHEN** 用户登录后依次进入今日、任务入口、会话历史/Run、两类批准、提醒任务和活动，再进入账户及退出流程
- **THEN** 每个页面均采用重建后的布局、组件与交互规则，真实内容/操作完整可用，不存在仅改对话或其余页面仍停留旧 Demo 的交付

#### Scenario: 跨页面共享交互与窄屏导航（D8）

- **WHEN** 用户以键盘在桌面和约 375px 窄屏操作表单、菜单、导航及弹层
- **THEN** 组件保持一致的可访问交互、字段反馈和焦点返回，主要资源均可达；采用 LumenUI 不使整站被迫客户端化，不以默认组件样例替代产品页面

#### Scenario: 重构后原账户与历史继续可用（D5/D8/D9）

- **WHEN** 原用户重登并打开既有会话、Run、提醒或文档批准深链
- **THEN** 新界面读取同一 owner 的原事实，冻结批准内容不变，不重建账户、不重新批准或自动执行；完整前端重构不改变认证、CSRF、精确批准、取消和 unknown 保护

#### Scenario: 组件库切换不改变显式执行与焦点合同（D5/D8）

- **WHEN** 用户通过 LumenUI 菜单、筛选、资料选择、账户表单和活动流离开确认操作页面
- **THEN** 页面与 portal 使用同一官方主题；筛选仍为 GET，选择资料不默选或发送，只有明确提交才执行；离开确认先聚焦取消，取消后保持连接并返回来源触发器，原认证、冻结批准和业务状态规则不因组件切换改变

#### Scenario: 对话首次读取保持同一布局（D8/D10）

- **WHEN** 用户首次直接打开或从导航进入对话路由，页面仍在读取
- **THEN** 使用与对话栏、消息区和底部输入对应的独立加载骨架，不先展示首页欢迎/简报或旧布局；加载仅表达读取，不提供假的业务操作，不清除用户存储或自动发送

#### Scenario: 直接使用原生玻璃材质（D8）

- **WHEN** 页面呈现输入、已有消息面板、菜单或其他浮层
- **THEN** 使用组件库默认主题和原生材质接口，不添加应用主题 token、surface slot 描边或手工模糊/阴影；组件库未提供的效果不另用 CSS 仿造

### Requirement: 面向用户目标的确定入口

系统 SHALL 默认提供真实 Agent 对话，无需先选择工具或工作区；同时保留“创建提醒 / 处理资料”明确快捷路径，不要求理解 business/harness，不静默切换执行器。资料任务展示服务端登记的有限可读/可写范围及受管副本边界。方案见本 change design.md §2、§6；既有 workspace 授权和执行合同不变。

#### Scenario: 选择目标再明确发送（D8）

- **WHEN** 用户直接进入对话，或选择提醒/资料快捷目标并填写消息
- **THEN** 普通交流使用原生 Agent 且不要求资料登记；选择和填写本身不执行；明确发送时提醒快捷入口走原业务路径，资料必须由用户显式选择已读取的真实登记后走原 Harness，不能默选首项；表单入口 query 不修改历史 Run，不因目标切换继续旧 Run 或重发旧消息

#### Scenario: 模型或资料不可用（D8/D10）

- **WHEN** Agent 路径缺模型/运行依赖，或资料路径没有可用登记、登记读取失败、当前授权被拒绝
- **THEN** 展示有事实依据的不可用原因和配置/读取指引，不假报空资料或成功，不切换到提醒或其他模型，不允许输入任意宿主 root 扩权

### Requirement: 常驻输入与连续会话

系统 SHALL 在首次发送、运行中和运行结束后保留可达的对话输入面；完成后可在同一会话明确发送下一轮。连续消息来自已存可见消息与原运行事件，不凭文本相似度猜测关联或重复拼接最终档案与同一流式回复。新 Harness 运行在接纳时冻结同用户、同会话最多63条前序可见 user/assistant 消息及本轮完整输入，按冻结顺序执行和批准恢复；不是永久记忆，不重放旧工具调用。

#### Scenario: 不选工具的多轮交流（D8/D10）

- **WHEN** 用户直接发送普通问题，收到回复后在原页面追问
- **THEN** 输入不消失，页面保留前轮消息与本轮回复；第二轮沿原 conversation_id 新建 Run，模型收到接纳时冻结的前轮可见上下文及完整当前输入一次，不混入其他用户、其他会话或 system 消息

#### Scenario: 刷新后明确追问（D8/D9）

- **WHEN** 用户刷新、重登或从历史发现原会话，再输入下一条消息
- **THEN** 加载和历史恢复只有 GET；输入面仍可达，只有用户明确发送才创建新 Run，新运行使用同会话已存可见上下文，不重发旧消息或自动恢复旧执行

#### Scenario: 在途和未知状态保留边界（D8/D9）

- **WHEN** 原运行仍在执行、等待批准、发送结果待核实或工具效果未知
- **THEN** 输入面继续展示真实不可发送原因，不能通过发送新消息绕过原运行；继续和取消仍走原 Run 的明确操作，不把输入新文本当成批准或恢复

#### Scenario: 有界窗口与批准恢复（D5/D8/D9）

- **WHEN** 会话历史超过64条消息，或原批准等待后又出现后来消息
- **THEN** 新运行只保留接纳时最新63条前序可见消息及完整当前输入；批准恢复沿原冻结引用，不混入后来消息，不截断当前输入，超1MiB聚合帧明确失败而非成功或切换模型；没有跨轮冻结引用的历史 Run 不因恢复补造上下文

### Requirement: 常用 Agent 的真实流式聊天体验

系统 SHALL 将模型供应商生成中的可见增量经原生 Harness 和 TS 接受/持久化后立即投影既有 SSE，而非等待完整回答后拆分或用前端打字动画伪装。聊天采用可滚动消息区与视口底部常驻输入，流式与历史助手文本共用安全 Markdown；提醒和资料工具收进输入框左侧加号菜单。运行技术信息默认折叠，必要的批准、明确继续与未知效果提示仍可见，不改变原事实与执行归属。

#### Scenario: 模型未完成时已经出现回复（D8）

- **WHEN** 模型已产生可见正文但尚未返回最终片段和用量
- **THEN** 原生运行逐次接受真实增量，用户已经看到逐渐增加的格式化回复；最终消息不重复追加，部分正文不被当成成功或工具回执

#### Scenario: 输入框工具与键盘（D8）

- **WHEN** 用户点击输入框左侧加号、选择提醒或资料，或用键盘关闭菜单和输入多行消息
- **THEN** 工具菜单可键盘访问并返回焦点，选择本身不发送；资料仍须显式选择已读取的登记，Enter明确发送，Shift+Enter和输入法确认不误发，生成中停止仍按原取消回执合同

#### Scenario: 长回复与窄屏阅读（D8）

- **WHEN** 回复包含标题、列表、长代码和表格，或用户在375px窄屏向上查看前文
- **THEN** 内容安全格式化且不造成整页横向溢出，输入和发送/停止保持可达；用户离开底部后不强制追尾，并可明确回到最新

#### Scenario: 默认中文与明确语言切换（D8/D10）

- **WHEN** 普通消息未明确指定回复语言，或用户明确要求本条用其他语言回复
- **THEN** 原生系统上下文指示默认简体中文、明确语言要求优先；不靠前端翻译或伪造回答，不强制改写代码和专有名称

### Requirement: 统一资源导航与可发现的真实范围

系统 SHALL 在统一布局中组织账户、今日、对话、确认、提醒任务和活动，复用账户/历史真实能力及稳定深链；提醒列表与活动账不得冒充资料任务历史。方案见 design.md §2、§5–§6；时间只展示已接受的冻结字段，不重新计算或改写。

#### Scenario: 旧深链与导航（D2/D8）

- **WHEN** 用户经统一导航、既有会话/Run、批准或任务深链查看资源
- **THEN** 原资源与所属事实仍可读，当前页面和返回路径清楚，不要求发消息或重新批准；时间按既有冻结语义呈现

#### Scenario: 个人助理入口与分层收纳（D8）

- **WHEN** 用户登录后进入首页，或在桌面与约 375px 窄屏使用顶部导航
- **THEN** 首页以开始对话为主，提醒和资料是次级入口，今日简报可展开读取真实内容；导航以助理和事项组织，事项与账户的次级目的地按需展开，原提醒、确认、活动及账户仍可达
- **AND** 菜单支持键盘、关闭后返回触发器，打开菜单、展开简报或选择资源不触发业务提交；离开活动流仍执行既有确认与断连合同

#### Scenario: 简洁登录保留原凭据与保护（D8）

- **WHEN** 用户打开正式登录页并填写已有用户名和密码
- **THEN** 常驻表单突出字段与登录动作，密码可显示或隐藏，帮助说明按需展开；字段错误可定位，支持自动填充与粘贴
- **AND** 改版不替换原密码、不缩短兼容长度或改为明文存储；成功后仍沿安全返回路径只读恢复，不自动发送消息或批准

#### Scenario: 超过首批的提醒与活动（D8/D10）

- **WHEN** 提醒确认、任务或活动超过首批上限，或某任务的事件还有后续页
- **THEN** 提供沿既有游标继续读取的可达入口；活动明确区分任务范围索引与选中任务事件，各自保存游标和读取状态，不伪造全局全量时间线；不会丢弃后续页却声称全量，不扩成通用审计

### Requirement: 精确批准与显式继续原运行

系统 SHALL 清楚区分提醒确认与文档批准，展示完整冻结内容和真实结果；文档批准仅授权，之后由用户显式继续原 Run。方案见 design.md §3–§4；沿用 design/14 §5、§7 及 agent-runtime/workspaces，不增加自动执行路径。

#### Scenario: 完整预览与批准零写（D5/D8/D10）

- **WHEN** 用户在窄屏或桌面审阅并批准文档修改
- **THEN** 基线/目标版本、完整 before/after、完整目标正文及冻结批准正文均可读；确认只取原 preview.body 字符串，不从 DOM、diff 或摘要重建，不因排版 trim/归一内容；批准不产生文件写入或宣称保存成功

#### Scenario: 批准早于挂起或当前不可继续（D8/D10）

- **WHEN** 批准已经提交，但原等待点尚未提交或 Run.can_resume=false
- **THEN** 保留已读授权事实，提供只读刷新，不一概称为尚未批准，也不猜测原因或自动继续；只有显式动作按原服务端资格进入继续请求

#### Scenario: 批准链接不误断主动流（D8）

- **WHEN** 原 Run 的主动流仍连接，用户打开批准详情
- **THEN** 保持原有独立打开批准页和原会话上下文的合同；正常批准挂起 EOF 不被误报为取消，之后继续仍绑定原 Run 而非新消息

### Requirement: 效果与运行状态依据可信事实

系统 SHALL 从 Run、决议和工具效果呈现等待批准、已授权未保存、当前可继续、结果待确认、applied、verified、conflict、unknown 及取消；模型措辞和前端本地旗标不得作为保存或核对证据。方案见 design.md §3、§6；不新增执行事实表、SSE 事件体系或前端领域状态机。

#### Scenario: 已授权、applied 与 verified（D8/D10）

- **WHEN** 同一文档先为 approved/not_started，随后为 applied，最后具有新的全文读取 verified
- **THEN** 各阶段展示对应事实；授权不称保存，applied 不称已核对，只有已接受的新读取证据才呈现 verified

#### Scenario: 冲突与未知效果（D8/D10）

- **WHEN** 原动作有可信零写 conflict，或效果为 unknown
- **THEN** conflict 保留原动作未写入及新批准需求；unknown 明确可能已生效且禁止盲重做，不凭当前文件相同或模型回答把原调用改成成功

#### Scenario: 取消与阶段不可确认（D9/D10）

- **WHEN** Run 已取消但此前可能已有文件效果，或没有可信处理阶段
- **THEN** 取消不宣称回滚既成效果，终止连接不冒充取消回执；无阶段事实只展示处理中或结果待确认，不编造进度

### Requirement: 错误恢复不自动产生副作用

系统 SHALL 准确区分未认证/会话失效、权限拒绝、资源不存在、连接/依赖故障及已知领域错误，提供相应恢复动作。查看、分页、刷新、回退和重登恢复仍严格只读，不重放消息、批准、继续、取消或写文件。方案见 design.md §3，沿用 identity 和 conversations 只读恢复合同。

#### Scenario: 401 与其他错误（D8/D10）

- **WHEN** 请求为 401、403、404、连接失败或 503
- **THEN** 只有真实 401 引导安全站内返回的正式重登，其他类别保留真实原因，不将其统一当作会话过期、空数据或模型缺配置；成功重登仅 GET 原事实

#### Scenario: 副作用响应丢失或流中断（D8/D9）

- **WHEN** 发送、继续、批准或取消响应丢失，或主动 SSE 中断
- **THEN** 保留已接受事实并引导读取原状态，不自动补发 POST、换 Run、换幂等键或重写 unknown；后续显式动作仍遵守原幂等、断连取消及权限合同

### Requirement: 复杂交互具有唯一状态与生命周期归属

复杂对话与批准交互 SHALL 随真实功能切片分离 View、功能级 hook/controller 和 Model/数据访问；page/layout 保留路由/组装与 Server/Client 边界。View 不编排发送、SSE、继续、取消和历史恢复；公开合同仍为事实来源，不强迫简单只读页新增空层。方案见 design.md §4。

#### Scenario: 调整界面与保持交互（D1/D8）

- **WHEN** 调整任务表单、回复、状态或操作区布局和样式
- **THEN** 不需同时改变发送、SSE、继续/取消与恢复编排；前端复用公开 schema 和现有数据访问，不引用 API 私有源码、不建立第二批准/执行事实来源

#### Scenario: 卸载、切换与迟到响应（D8）

- **WHEN** 用户卸载对话、切换任务或重新登录，旧 GET/SSE 存在迟到数据
- **THEN** 旧订阅清理，旧任务不能更新新任务的界面，不能残留订阅产生重复动作；生命周期变化不自动执行业务操作，既有断连取消合同不被静默改变

### Requirement: 可访问的完整内容与真实异步状态

主要页面 SHALL 支持键盘、可见焦点、约 375px 窄屏、字段错误关联和适当状态播报；加载、空数据、禁用、分页与部分失败均基于真实请求。长路径、长文档及精确批准内容保持完整可达。方案见 design.md §5、§7。

#### Scenario: 键盘与窄屏完整批准（D5/D8）

- **WHEN** 用户用键盘在约 375px 窄屏查看导航、表单、长路径及完整批准内容
- **THEN** 可发现并操作关键入口、看见焦点，字段有标签，错误可定位；内容不被溢出、固定操作区或省略裁掉，冻结字节不因排版改变

#### Scenario: 加载与局部失败（D8/D10）

- **WHEN** 某资源加载中、确实为空、动作不可用，或原文成功而批准/后续页读取失败
- **THEN** 显示对应状态及原因，保留成功内容和未推进游标，提供仅针对失败资源的 GET 恢复，不报完整成功或空历史；关键状态变化可被辅助技术感知
