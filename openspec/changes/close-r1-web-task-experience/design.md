# #70 基于 shadcn/ui 的 Web 完整重构方案

> 状态：Proposed；用于独立 OpenSpec-only 评审，不是实施或验收记录。
> 范围：R1 全站 Web 信息架构、应用布局、全部页面、shadcn/ui 组件与 Tailwind 样式基础、交互反馈和 React 职责重构。
> 不包含：启动/认证/历史后端重做、R2、新执行机制、自动恢复或用户安装配置变更。
> 阶段：先评审体验与必要合同，再按完整用户切片实施。

## 1. 已确认的基线与前置条件

Observed：本地基线 `e3f121b`；#67、#68、#69 均已关闭。复用 [生命周期指南](../../../docs/local-lifecycle.md)、[账户验证](../../../docs/account-access-verification-2026-10-27.md)、[历史验证](../../../docs/conversation-history-verification-2026-10-28.md)及各自 OpenSpec 归档，不重跑无新增价值的模块验收。Issue/父跟踪的旧勾选或“只规划”措辞不能代替合并产物和版本化证据。

Required（用户明确方向）：以自有 LumenUI（shadcn/Base UI）与 Tailwind CSS 完整重构 Web，而非在原 Demo 上优化或换皮。旧页面布局、配色、控件和组件目录没有必须沿用的约束；后端能力、数据身份、公开业务合同及安全边界继续有效。以下现状仅作迁移依据，不作为视觉目标或重构范围上限。

- `apps/web/src/app/layout.tsx` 已有六个资源目的地和跳到正文链接；重建导航结构与应用布局，保留这些能力的可发现性和已有资源地址，不保留旧页眉结构。
- `conversations/page.tsx`、`HistoryList/HistoryDetail/HistoryResource/ApprovalHistory` 已交付发现、分页和局部 GET 恢复。新任务与历史定位仍需分清。
- `conversations/Chat.tsx` 同时持有消息、Run、请求、取消键、继续键、订阅与 JSX；新发送使用 business/harness 选择器，`can_resume=false` 提示将所有原因称为等待批准。新实现按功能状态归属重新组织，不以仅抽出 JSX 或沿用旧大组件为完成。
- `lib/conversation-run.ts` 已有 envelope/SSE/Run 读取、事件去重和跨 Run 聚合；`document-loop.ts` 已有精确确认 body、批准链接和全部效果标签。`lib/api.ts` 保留 HTTP/code/requestId，账户导航已有安全返回位置；这些能力优先复用。
- 旧 `globals.css` 及原生控件是待替换的展示实现，不作为新视觉基础；可复用的是焦点、冻结内容换行等有效行为要求。新设计采用 shadcn/ui、Tailwind CSS 和统一语义变量，不要求保留暖灰/深绿配色。
- `approvals/page.tsx`、`tasks/page.tsx` 和 `activity/page.tsx` 固定读取首批 50 条但未使用 `next_cursor`；活动还丢弃每个任务事件的后续游标。活动的事件读取使用 `Promise.all` 并发，不是串行；问题是范围不完整，而不是需要新建活动审计平台。

准备阶段的真实页面观察（2026-10-28）：共享包构建成功；以现有 Web `dev` 入口观察 `/conversations` 和“新对话”，确认仍展示内部执行方式。375px 下所观察页面文档宽度等于视口宽度，不能据此断言所有批准内容均适配。只进行页面查看及 GET，没有发送、批准、继续、取消或模型请求。

运行边界：正式 `local:start` 返回 `CONFIG_MISSING`，因此未建立受支持安装；现有 3000 服务经 Web proxy 的历史集合 GET 返回 404，而 `/me`、工作区 GET 为 401。[INFERENCE] 该服务不具备当前历史集合合同，原因及部署版本尚未核定，不能当作 #69 源码回归。未新建/接管安装、读取或改写秘密。实施后的正式集成需定位原安装配置并按既有入口准备同批 API/Web/native/MCP 与 PG，不用开发页面观察替代正式验收。

可复用验证边界：`apps/web/test/conversation-run.test.ts` 保护批准挂起 EOF、事件去重和真实 HTTP/proxy 消费；`document-loop.test.ts`、`conversation-history.test.ts`、`history-read-http.test.ts`、`history-read-error.test.ts`、`account-navigation.test.ts` 是文档纯转换、历史与认证恢复的现有覆盖入口。实施前按实际改动核对断言，不把测试文件存在当作全部交互已覆盖。

## 2. 用户入口与信息层级

重新设计面向日常交流的个人助理，而不是工具工作台。保留“今日、对话、确认、提醒任务、活动、账户”的能力覆盖，以主次分明、按需展开的入口组织；不建立新的综合任务事实后端。

| 页面                  | 主要内容与动作                                                               | 必须保留的边界                                                         |
| --------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 首页 `/`              | 个人助理欢迎、开始对话主入口；提醒/资料次级入口与可展开今日简报              | 简报只读真实投影，保留日期、时区、过期和失败；不把摘要称为全部任务     |
| 对话 `/conversations` | 默认真实 Agent 交流、常驻输入；保留提醒/资料快捷入口及可发现历史列表         | 加载历史只读；明确发送才执行，原 conversation_id/run_id 深链和分页不变 |
| 指定会话/Run          | 连续消息与下一轮输入；指定原话、真实状态、相关批准/效果和原 Run 操作独立核对 | 原 Run 选择不改执行种类或冻结 workspace；多个 Run 不串状态             |
| 确认 `/approvals`     | 明确标注提醒确认；文档批准由原 Run/历史链接进入独立详情                      | 不虚构已有文档批准集合 API；两种批准不共用错误的时间/结果语义          |
| 任务 `/tasks`         | 明确是提醒任务，状态与真实回执、取消入口                                     | 不充当资料历史，不承诺通知必达                                         |
| 活动 `/activity`      | 提醒事件账及真实任务定位                                                     | 不扩为通用 Agent 审计；未加载部分与全量区分                            |
| 账户与认证            | 重建账户、登录、首次建号、原身份转正和退出界面，统一字段/验证/恢复体验       | 复用原认证 API、Cookie/CSRF、身份保留和只读返回；退出失败不伪报撤销    |

对话默认使用已有无 workspace 的 Harness，普通交流无需预选工具或资料登记；输入区在发送、执行中和结束后持续存在。创建提醒固定映射 `business`，呈现日期/时间/时区要求；处理资料固定映射带显式 workspace 的 `harness`，呈现目标、真实登记项、可读/可写相对范围与受管副本说明。选择目标本身不发送请求。资料任务须明确选择可用登记，空登记提供本机配置指引，不允许模型猜范围或用提醒路径兜底。

页面沿用原 URL；同一会话完成后可以明确发送下一轮，沿原 conversation_id 新建 Run，不因选中或刷新资源自动执行。连续消息以已存 user/assistant 档案和当前运行事件为依据，不能把相似文本猜成某次运行，也不能重复拼接最终档案和同一流式回复。执行中、等待批准、发送结果未知或效果未知时保留输入及不可发送原因；原等待点仍须显式继续，不以新消息绕过。

新 Harness Run 接纳事务内将本人同会话最新63条可见消息与完整当前输入的引用冻结到既有 frozen_context，总数最多64条；按 PostgreSQL created_at/id 排序后追加当前输入一次，不带旧 tool_calls 或原始工具结果。初次执行和批准恢复使用同一冻结顺序，后来消息不改变原运行；历史旧 Run 缺跨轮引用时仍保持原输入语义。窗口不等于永久记忆，完整消息及工具/观察超过1MiB仍明确失败，不按字节截断输入、不换模型或执行器。不新增HTTP DTO、迁移、执行种类或记忆服务。

保留 [对话 API §3](../../../docs/api/conversations/conversations_routes.md#3-只读补读run-状态取消与有限恢复-required) 的连接语义：打开批准详情仍独立新标签，不因跳批准页提前关闭尚在进入等待点的原流；用户主动离开运行中的 SSE 仍可能导致服务端持久取消，界面必须说明这个后果，不以“后台继续”的措辞改变合同。正常挂起 EOF 不当取消；读取历史不另开主动流。

### 2.1 个人助理的日常交流

采用官方 Linen 浅色画布、蓝色操作和深色正文，普通交流以连续对话和常驻输入为主，资料审阅与真实结果保留独立阅读区域。不新增运营仪表盘、装饰图表、提示词商店、模型切换器或同权重统计卡。蓝色表达操作与定位，绿色只表达有证据的核对。

- 顶部一级入口只有 **助理、事项**；助理进入 `/conversations`，事项菜单收纳今日安排、我的提醒、待我确认与活动记录，记录与日常操作分隔。账户在独立头像菜单显示真实 display_name，不用 UUID 作为头像文字。品牌“Along”回首页，不放未取得全量事实的红点或计数。
- 首页以开始对话为主，创建提醒与处理资料降为次级快捷入口；今日简报默认收起，展开读取已有真实内容与范围提示。登录页只常驻欢迎、用户名、密码和提交，输入内显示/隐藏，维护和返回说明收进帮助。密码兼容规则与哈希存储不变，不因界面调整替换已有口令。资料结果回原对话找，不在提醒任务里伪造另一类 task。
- `/conversations` 无身份 query 提供默认对话及会话发现；`conversation_id` 定位可继续交流的会话；加 `run_id` 可核对指定运行。目标选择为页面内状态，今日链接可使用纯展示 query `intent=reminder|document` 预选；已有身份 query 优先，`intent` 绝不能修改历史 Run。未知值不执行，不增加后端参数。
- 会话列表沿服务端建立时间倒序，明写“按建立时间”；Run 按建立时间正序。列表不提供无后端能力的“全局搜索”或“最近活跃排序”。标题用服务端 title，缺标题用“会话＋短号”；Run 用可信原话首行作导航摘要，旁列状态、建立时间与辅助短号。摘要不代替详情原话，也不按时间/相似内容猜关联。
- 指定 Run 默认展示原文、回复、全部已读批准及结果。状态区可见，副作用操作需显式展开“此运行的操作”；展开只 GET。正常阅读不需要展开操作，批准返回后的下一步也不会藏在不明图标中。
- 直接打开批准详情时，依据详情自身 conversation_id/run_id 生成返回链接，不信任 URL 里不匹配的上下文。无可靠原会话引用的旧提醒只给“返回提醒确认”，不猜原 Run。文档批准无集合页；其入口是原 Run 的“修改与结果”，不是提醒确认中的假标签页。

### 2.3 核心链路与屏幕线框

以下是可评审的布局稿，不是运行截图；方括号表示交互，示例“资料甲”“brief.md”仅表达版式，不代表用户资料或已读取事实。线框中正文占位在实现中必须替换为**完整实际字段**，不能按稿截断。

**A. 个人助理首页**

```text
┌ Along. ─────────── [助理] [事项 ▾] ───────── [账户] ┐
│                                                    │
│   你的个人助理                                     │
│   今天，想一起做点什么？                           │
│   从一个问题、一个想法，或一件想做的事开始。       │
│   [开始对话 →]                                     │
│   也可以  创建提醒  处理资料                       │
│                                                    │
│   今日简报                                      ▾  │
│   提醒、待确认与已记录的结果                       │
└────────────────────────────────────────────────────┘
```

对话默认采用居中的消息区和视口底部输入框；用户消息为气泡，助手回复以 Markdown 呈现，空态只有简短问候，不展示运行教程或三张目标选择卡。

```text
对话                                      [历史会话] [新对话]
────────────────────────────────────────────────────────────
                              用户消息气泡
助手回复：标题、段落、列表、代码与表格
模型仍在生成时，真实增量已经出现在这里
                                        [回到最新 ↓]
────────────────────────────────────────────────────────────
┌ 输入框：多行消息；Enter发送，Shift+Enter换行 ┐
│ [＋]                                [↑]   │
└───────────────────────────────────────────┘
```

1. 输入框左侧「＋」通过可键盘操作的菜单提供创建提醒、处理资料和普通对话；选择工具只改变待发消息，不发送。已选工具显示可移除标签。普通对话不要求工具或工作区。
2. 资料工具在输入框内要求显式选择服务端读取成功的登记；范围列表与受管副本说明按需展开，长列表在有界区域内滚动，不挤掉输入和发送。空登记与读取失败分别呈现，不默认选首项、不接收任意宿主 root；无写范围可做只读任务。提醒工具显示已确认时区边界，保留重复时刻候选及明确提交，不以选择候选代替确认。
3. 只有明确发送才新建消息和 Run；IME确认和 Shift+Enter 不提交。生成时提供原 Run 的停止操作，不拿断开连接当停止回执。发送结果未知仍保留同键显式处理，不能另开同目标任务绕过。

**B. 处理、待审阅与原 Run 继续（1440px / 375px）**

```text
桌面与375px共用同一聊天结构
┌────────────────────────────────────────┐
│ [导航] 对话        [历史] [新对话]      │
│ ┌ 可滚动的消息区 ───────────────────┐ │
│ │ 既有消息与实时 Markdown 回复       │ │
│ │ 必要的批准/继续、未知效果提示       │ │
│ │ [运行事实 v] [批准与结果 v]        │ │
│ └───────────────────────────────────┘ │
│ [已选工具 ×]（可选）                   │
│ [消息输入                             ]│
│ [＋]                             [↑/■]│
└────────────────────────────────────────┘
```

输入区不随消息滚出视口；消息区独立滚动，用户向上阅读时不强行追尾，并提供“回到最新”。运行编号、可信原话引用和原事件文本默认折叠；等待批准、可明确继续或工具效果未知时，必要操作与说明直接呈现，不靠模型文字推断权限。工具和错误区域有界滚动，窄屏保留完整输入、发送与停止。

4. 处理中事实栏只显示 Run 当前事实，无可信阶段不画进度百分比或“正在保存”。助手说“已完成”也不能替换效果区。用户向上读历史时不被新 token 强制拉到底；底部有“有新内容”跳转，状态播报按阶段而非每 token。
5. 收到批准事件后出现带种类的审阅行；新标签链接保留原流。正常挂起 EOF 表示等待，不渲染断流错误。批准页显示授权结果后，主按钮变为**“查看原运行”链接**，文字说明“回到原标签页读取状态，再明确继续”。不尝试脚本自动切原标签、不关原流、不发 resume；独立深链返回也只 GET。
6. 原 Run 读到 approved/not_started 后显示“已授权，尚无保存结果”；同时 `can_resume=false` 时按钮禁用，解释“当前不可继续，读取最新状态”，不说“尚未批准”。若已知 status=running，可说明“运行仍在处理”；不把它断言为等待点尚未提交的唯一原因。只有最新资格与原有效等待点成立时，用户点击继续才复用原 checkpoint/幂等合同启动同 Run 新 attempt。
7. 正在继续时主按钮改“正在继续”，禁用二次点击。`reserved` 为“结果待确认”，`applied` 为“已记录写入，尚未完成后续全文核对”，`verified` 才用绿色小标记“已保存并核对”。保留目标、版本和可展开的 apply/read 引用。多个批准逐项列结果，不因一项 verified 给整次 Run 盖成功章；Run 终态与文档效果分别显示。
8. 退出再登录，用户从会话列表按标题/建立时间发现原会话，再选 Run。默认只读，保留原话缺失/关联异常、事件未读完、批准局部失败。消息档案为独立入口，标注“已存消息；不声明与所选运行的对应关系”，不将 assistant 档案重复拼到 Run 回复。

**C. 文档审阅校样页（全页，不是弹窗）**

```text
[原会话 / 此次运行]                 文档批准 · 等待审阅
审阅对 brief.md 的修改
相对目标（完整） · 工作区标识/已核验原冻结名称

页内目录：[改动对照] [完整目标] [批准正文] [执行证据]
01 改动对照
替换前（完整 preview.before） | 替换后（完整 preview.after）
窄屏按先前后后上下排列；红/绿之外使用“移除/新增”标签
02 完整目标
exact_new_content 全文，非可编辑，保留空白和软换行
03 本次冻结批准正文

─────────────────────────────────────────────────────

```

不以滚动到底或勾“已读”创建新的授权条件；完整正文成功加载、身份与现有动作条件满足才可提交。确认调用只取 detail.preview.body 原始字符串，`pre-wrap`/高亮/换行只是展示；不从 DOM 复制、trim、Markdown 渲染或 diff 重新生成请求。若展示解码/校验失败，不提供批准按钮。无独立 diff 字段时，使用可信 before/after 做纯展示对照并明确不是补丁指令，不能隐藏未变化正文。正文按区块自然滚动，页内目录不遮正文，底部操作不粘住；长文本可以读到最后一字。

批准成功后不跳走，原位置保留全文和“已授权，尚无保存结果”，去掉可重复决议操作，提供原 Run 链接。结果读取失败时保留已接受授权、标“效果尚未读取”，不可用旧 not_started 覆盖未知最新效果。拒绝后只读显示已拒绝，返回原 Run 按既有资格决定是否显式继续处理决议，不自动生成同义新提议。

## 3. 可信状态、批准与恢复

显示模型回答与系统事实的不同区域。不显示推测的“检索 50% / 保存 80%”；没有可信阶段时只显示“处理中”。下表是公开事实的展示投影，不是前端状态机，也不增加持久状态。

| 事实来源                        | 用户能确认的事实                             | 允许的引导                                                                      |
| ------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------- |
| Run 读取中或失败                | 结果尚未确认，保留已读内容                   | 重新读取 GET；不可由本地标志判断完成                                            |
| document pending                | 等待用户审阅                                 | 打开完整冻结预览，明确批准或拒绝                                                |
| document approved + not_started | 已授权，尚无保存结果                         | 返回原 Run，读取当前资格后显式继续；不从批准页自动执行                          |
| Run.can_resume=true + 原等待点  | 原运行当前可继续                             | 用户点击继续才发送绑定原 checkpoint 的请求                                      |
| can_resume=false                | 原运行当前不可继续；不能单凭该值判定 pending | 结合已读取决议说明已知事实；原因不明时只说不可继续并提供 GET，不猜撤权/批准原因 |
| reserved / 请求断流             | 已预约或执行结果待确认                       | 读取原 Run/效果，不把断连当失败或取消回执                                       |
| applied                         | 写入结果已接受，尚无后续新全文读取核对       | 不显示 verified 或“全部完成”；仅按原运行合同推进                                |
| verified                        | 写入结果已接受，随后有新全文读取核对         | 显示已保存并核对及真实目标/证据，不宣称产物永不变化                             |
| conflict                        | 原动作明确零写冲突                           | 保留原失败事实；新的读取/提议和批准沿既有原 Run 合同，不一键覆盖                |
| unknown / TOOL_EFFECT_UNKNOWN   | 可能已生效，原动作不能安全重做               | 只读查看与维护说明；不提供盲目重写/重发原动作                                   |
| cancelled                       | Run 已取消，不等于撤回已发生文件效果         | 同时保留既有效果事实；abort 连接本身不等于取消成功                              |

提醒确认仍读取完整冻结展示与真实 task/后继引用；文档详情保留基线/目标版本、差异、完整目标正文和原 Run。摘要、折叠卡片或 diff 不能替代完整批准正文；确认 body 继续由原 `documentConfirmBody` 读取冻结 `preview.body`，不得从 DOM 排版、重新序列化正文或模型摘要拼出。

错误由数据访问边界保留 HTTP、领域 code 和可用诊断标识，View 显示简明解释和相应动作：401 正式重登后只读返回；403 解释权限/CSRF，不跳登录掩盖；404 说明目标或接口不可用而非空历史；连接失败/503 与模型未配置、工作区无登记/撤权分别呈现。只有真实 code 支撑时才命名具体原因；不能把任意 503 断言为缺模型。所有副作用丢响应先读事实，沿原幂等合同显式处理，不自动换键、换 Run 或补发 POST。

### 3.1 失败画面的固定位置与动作门

所有错误靠近所属资源；页首只汇总会阻止整页读取的错误。Alert 固定保留到该资源成功读取或用户明确离开，不仅 toast。诊断区可展开 HTTP、领域 code 和允许展示的 request_id，不放 provider 原文/宿主路径/认证材料。运行信息、授权决议、文件效果各有自己的“已读/未读/读取失败”，不将多个 GET 拼成原子快照。

| 可信输入                              | 画面与保留内容                                                        | 可用动作 / 禁用边界                                                                                                             |
| ------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 受保护 HTTP 401                       | 登录提示，说明会话无效；保留安全站内 returnTo，停止使用过期动作上下文 | 正式登录；返回仅 GET。清本应用动作重试状态，不存正文/口令作恢复依据；流内领域401不自动当登录失效                                |
| 403 / 明确 CSRF 拒绝                  | “当前请求无权执行”或对应明确 CSRF 说明；不透露他人信息                | 回自己的列表、重新读取身份/资源；无登录重定向、无自动重试POST。冻结历史能读不代表新动作获权                                     |
| 404                                   | 详情“未找到此资源”；集合接口404则“历史暂不可读取”，不是“没有历史”     | 返回所属列表/重新 GET；不从错误创建替代资源                                                                                     |
| 网络失败、503、无效响应               | “服务暂不可读取/响应无法核验”，带允许诊断；成功区不消失               | 仅重读失败资源；未知认证状态不开放初始化。禁止把任意503写成模型缺配置                                                           |
| `HARNESS_UNAVAILABLE`                 | “资料处理能力不可用”；只有更具体可信信息才说明模型或 native 原因      | 保留目标输入、重读可读取的资料范围；可手动再次提交原安全操作仅按既有合同，不自动切提醒/模型。未有健康接口不伪装启动前模型就绪灯 |
| 工作区 GET 空、GET失败                | 分别为“没有可选登记”与“范围未读取”；均不展示文件空目录                | 读取登记、查看账户中的本机维护说明；目标可编辑，资料发送禁用。不得上传任意 root                                                 |
| 明确登记撤销/授权变化                 | “当前授权不允许继续此动作”；旧原话、冻结范围和既有效果仍可读          | GET、返回、符合原合同的安全停止；不换登记恢复旧 Run。仅 can_resume=false 时不得自行命名撤销                                     |
| `PRESENTATION_MISMATCH`、过期、已替代 | 错误定位到审阅动作；原正文保留并标失效/不一致                         | GET 当前/真实后继，重新审阅后用户决议；禁用旧确认，不自动接受新版本                                                             |
| 可信零写 conflict                     | 橙色“此版本未写入”；旧 approved 状态仍保留                            | 已有后继则查看后继；无后继只读原 Run/效果。新读、新提议、新批准由原执行合同推进，不提供UI覆盖写按钮                             |
| unknown / `TOOL_EFFECT_UNKNOWN`       | 橙色高优先 Alert：“可能已写入，原动作结果未知”；不是普通失败红字      | 读取原事实、查看安全诊断/维护说明；无重做、覆盖、另开同目标按钮。新读相同 hash 也不改原调用状态                                 |
| Run cancelled                         | “运行已停止”及“不会撤回已发生效果”；并列显示已知文档效果              | 只读；停止响应未确认则“停止结果待确认”，先 GET，不能凭 abort 显示成功                                                           |
| 主动 SSE 非正常断开                   | “连接中断，运行/效果需重新读取”，保留已收到内容                       | 原 Run GET；不自动重连执行、不自动resume。离开活跃页前说明关闭连接会按合同触发持久取消，不承诺后台继续                          |
| `failed` / 预算停止                   | 展示真实终态与可公开错误，文档效果另外判断                            | GET、返回；无可信零写证据不能承诺“没有改动”。不提供通用“重新运行”绕开 unknown                                                   |

主动页面内导航在确有活动流时显示短 AlertDialog：“离开将断开当前执行连接，服务端按取消合同处理；已发生的文件效果不会撤回”，默认焦点“留在此页”，另一动作“离开并断开”。关闭浏览器/刷新只能利用原生离开提示，不能保证拦截；不将提示本身当取消回执。不对历史只读页面拦截导航，也不在审批链接（新标签）上弹离开确认。

## 4. React 关注点分离

采用功能级 hook/controller 的 React MVVM 关注点分离，整体重新组织前端，而不是仅提取几个函数或替换控件。实施可按完整功能切片推进，但最终覆盖全站，不留下旧页面作为默认实现或长期双轨。以下为职责及建议名称，不以命名/文件数验收：

- **组装**：page/layout 保留 Server Component；选择 URL 身份、组合历史、主动对话和动作区域。不要把账户、简报、任务等只读页面全部客户端化。
- **功能控制器**：以 `useConversationTask` 拥有当前主动 Run、输入/目标、在途操作、SSE/GET controller、幂等键和派生展示；URL 拥有选中会话/Run 身份，每个响应核对身份。发送、读取、继续和取消的完整生命周期在此归属，View 不再编排请求。历史资源分页各自持有读取游标和错误，不塞入主动流控制器；批准决议由独立批准功能负责。
- **View**：以 shadcn/ui 基础组件组合任务输入、会话记录、状态/操作区、批准预览、资源列表与账户表单。功能组件接收展示数据和动作；焦点、展开等纯 UI 状态可留 View，发送/恢复编排不得回流到组件。建议 `TaskComposer`、`RunTranscript`、`RunStatusPanel` 等按任务语义命名，不逐一给旧 JSX 套 Card。
- **Model/数据访问**：公开类型与校验复用 `packages/contracts`、`stream-protocol`；`conversation-run.ts` 保留传输/解析与事件能力，必要时将其中请求职责集中而不产生逐函数空包装；`document-loop.ts` 保留文档纯转换。`api.ts` 继续服务端访问，不混入浏览器状态。派生标签可以是纯函数，不复制服务端领域授权规则。
- **历史与账户**：复用 #68/#69 的公开能力、只读语义和有效纯逻辑，重建其页面和交互，而不是因前序 Issue 已完成就排除这些页面。历史操作区消费同一对话控制能力，默认进入历史只 GET；账户重登后只读返回，不能因重构引入可写全局缓存或重复 Run。

卸载/切换时清理本功能 SSE 与 GET；旧响应只能更新它所属 Run，不能串到新任务。GET、发送、继续、取消分别拥有在途状态，避免按钮因无关读取永久禁用。取消以服务端返回为准再关闭连接；重登清除过期认证缓存而不自动重放业务动作。继续键继续绑定原 checkpoint，丢响应不能生成新消息或新 Run。提取过程不改这些现有合同。

建议在 `src/features/conversations`、`approvals`、`account` 内按实际功能聚合 View 与 hook；现有 lib 的有效纯函数可原位保留，不为目录整齐空转发。路由文件只组装，迁移一个切片就移除它的旧 View。具体最小责任如下：

| 功能边界                          | 拥有的状态/动作                                                                           | 明确不拥有                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `TaskComposer` / 对话控制器       | 明确目标、登记选择、原文、发送、原 Run SSE、继续/取消在途与原键；按身份清理请求           | 文档授权决议、全部历史缓存、服务端权限推演      |
| `RunTranscript` / 历史资源 hook   | 外部事件读取、seq去重、已读范围、每资源游标、局部 GET 重试；复用现有 HistoryResource 能力 | 自动开SSE、自动resume、从文本猜消息/Run关系     |
| `RunStatusPanel` / 同一对话控制器 | 展示 Run 事实、动作在途、显式继续/停止入口                                                | 自建另一个执行状态机；复制can_resume规则        |
| `DocumentReview` / 文档决议 hook  | 冻结detail、精确confirm body、决议幂等与响应不确定处理、独立效果读取                      | apply、文件读取、resume；不以多标签通信制造执行 |
| 提醒审阅/修改 hook                | 旧冻结正文、完整修改输入、时区候选、旧新批准关系、同键恢复                                | 客户端时间归一、原地修改已建任务、自动确认后继  |
| 账户表单                          | 对应窄账户操作、字段错误、在途状态、成功退出后的本应用状态清理                            | 自动认领/重建owner、存储口令、重放业务请求      |

只读今日、提醒列表/详情、活动、账户摘要不必各建 hook；Server Component 可以直接读取并渲染，分页和局部重读需要交互时再设最小 client island。普通 Table、文章、冻结文本、Empty、标题不是 Client 的理由。基础 UI 的展开/焦点状态不得反向成为已批准、可继续或已保存的事实。

## 5. 视觉与可访问性提案

### 5.1 组件与样式技术栈

使用自有 **LumenUI（shadcn/Base UI）+ Tailwind CSS**，在现有 `apps/web` Next.js App Router 内接入，不重新生成仓库、不引入第二 Web 应用。基础组件的唯一实现归 [LumenUI 上游](https://github.com/lorelum/lumen-ui) 所有；应用消费其固定 commit 生成的官方分发包，不复制或维护一套本地基础组件。

- 直接使用 `@lorelum/lumen-ui/components/*` 和官方 theme.css；分发包随 Web 源码保留并由单一 bun.lock 锁定，以支持无私有仓库凭据的冻结安装。包的来源 commit、构建入口与 SHA-256 记录在 Web README；升级库须重新生成官方分发包，不修改包内构建产物。
- 只保留单套 **Base UI + Linen 主题**，移除本地 Radix/shadcn 组件与旧 CLI 配置。LumenProvider 统一页面及 portal 主题；使用官方语义色和组件 variant/material，不逐页覆写组件外观。React 19、Next.js、RSC 与真实交互的兼容性须由本仓库构建和浏览器验证，不以同属 shadcn 推定行为一致。
- 完整批准正文放可深链访问的页面，不压进窄弹窗或 toast；工具事实与错误不能仅作瞬时通知。具体按需组件与使用边界见下表，不预装 catalog。
- Tailwind 负责布局、间距、断点和业务状态展示；语义 CSS 变量与组件材质由 LumenUI 官方主题拥有，不通过旧全局标签选择器覆盖所有按钮/输入框。菜单和弹窗沿官方 render、受控状态、焦点接口适配，不增加 Radix 兼容包装。
- 在既有 Bun workspaces 和单一 bun.lock 下管理包及 Tailwind/PostCSS；Docker 在冻结安装前复制 vendor 分发包。只按路径导入实际使用的组件，不新增应用级表单、图表或主题管理框架，最终不保留平行旧样式体系。
- [Tailwind 官方兼容表](https://tailwindcss.com/docs/compatibility)要求 Chrome 111+、Safari 16.4+、Firefox 128+。采用此现代浏览器基线；375px 是布局要求，不代表支持旧浏览器。`text-wrap:balance` 等只渐进增强，核心内容不依赖它。shadcn 接入只操作现有 Web，不执行新项目 scaffold 或复制其 monorepo 的 `packages/ui` 布局。
- 按当前需要使用 LumenUI Button、Input、Textarea、Label、Select、Radio、Checkbox、Badge、Alert、Skeleton、Table、Dropdown 与 Dialog；语义化原生 details/链接/正文无需机械替换。活动流离开确认保留 alertdialog 语义、取消优先焦点和菜单触发器返回；完整批准正文仍使用独立页面。

| 组件/表现                             | 用途与约束                                                                               |
| ------------------------------------- | ---------------------------------------------------------------------------------------- |
| DropdownMenu / details                | 事项与账户分层收纳、简报与登录帮助按需展开；保留键盘、焦点返回，不折叠批准正文           |

### 5.2 新的信息层级与视觉方向

采用官方 Linen 浅色主题，以清楚文字、克制表面与蓝色主操作组织日常阅读。页面标题不装卡；列表用行分隔；助手回复无气泡背景和机器人头像。欢迎与登录留白突出日常交流，维护说明降级收纳；输入区与审阅纸保留清楚边界。浅色为交付主题，不增加未验证的自动暗色或切换器。

- 约 375px 下长 ID/路径可换行，flex/grid 子项可收缩。冻结文档保留空白且可换行呈现，不截断正文、不省略批准关键字段、不修改提交字节。

## 6. API 与数据变更取舍

初始决定：不新增 API、表、SSE 或 Harness 协议。先复用 RunView、全部批准详情/结果、工作区摘要、事件和 #69 的资源读取。`can_resume` 不带原因并不强迫扩 DTO：无法确认时展示真实的“当前不可继续”足以避免误报。

只有某条已批准的展示/操作合同无法由现有读取实现时，才提出最小安全只读 DTO，写明来源、权限、字段/枚举和 strict 消费者清单，接受评审后再实施。不能凭 UI 本地旗标补造事实、泄露 root/私有登记摘要，或为了体验做通用进度事件。

提醒确认、任务及任务事件已有 `cursor/limit` 合同：本方案接通现有分页，而不是只加“首批”提示后留下不可达记录。活动按任务页与该任务的事件页提供有范围说明的读取入口，避免无界拉取所有任务/事件；保留已加载内容、失败任务及原游标，不将局部合并排序称为全局全量时间线。任务详情事件也必须可继续读完。文档批准没有集合合同，仍经 Run/历史访问，不为统一列表新建后台平台。

### 6.1 字段不足时的明确取舍

本设计可用现有公开能力落地，**没有必需新增 DTO**。具体缺口不以视觉推测填平：

| 页面想表达的信息       | 已核对来源/缺口                                                                   | 本方案选择与消费者                                                                                                                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 提醒任务的自然语言标题 | `lib/types.ts` TaskListItem/TaskDetail 无title；BriefCard/ApprovalListItem有title | 任务列表以冻结时间和状态为主，短号辅助；详情可用source_approval_id链接查看原批准，不为整页N+1补标题。若以后确需title，由tasks公共投影从冻结批准取得，另评审nullable只读字段及API/Web strict消费者，不能拿通知标题代替原任务 |

### 7.2 浏览器验收脚本与证据粒度

实施负责人持有每行唯一验证责任；集成负责人复核证据适用版本，只补跨模块缺口。以下是未来真实验收要求，不是本次已执行清单。

1. **视觉覆盖**：按 §5.3 全页面，在1440×900和375×812各取得新UI证据；短页全屏、长批准包含首部/中部/末部及完整内容可达记录。另以768px和200%缩放检查布局切换。观察阅读列宽、行密度、主要动作、长路径换行、无页面横向溢出；不能只截图Hero或空表单。
2. **键盘**：从跳到正文开始，Tab 走目标选择、资料选择、输入、主动作；事项/账户菜单打开、关闭和流中取消离开后焦点返回；错误摘要可定位字段；批准完整正文和底部动作可到达；密码粘贴/管理器不被拦。记录实际辅助技术检查范围，没用屏幕阅读器不声称已验证。
3. **资料正常链**：在受支持安装与获准材料上，从今日选择资料，核对真实读写范围；实际发送、审阅全部冻结字段、批准。关联同Run的批准前后文件/调用证据证明零写；返回后一次明确继续，证明唯一apply及新的全文read，UI才呈verified。不要为设计截图调用模型或制造用户资料。
4. **原流与早批准**：打开批准新标签不关闭原流；批准先于挂起时保留已授权且无自动resume；正常挂起EOF不显示取消；读到可继续后只一次用户动作。另观察主动导航离开提示与读取后的真实取消状态，不能以断开连接代替回执。
5. **范围与部分失败**：用获准测试环境的超过首批数据，逐页达到提醒第51项、任务第51项、某任务第51条事件、跨Run事件页的多个批准；只让一个GET失败，确认旧内容/游标保留、重读仅请求该资源。活动显示所选任务范围，不展示全局完整断言。
6. **错误矩阵**：受控HTTP/既有后端合同夹具可验证401/403/404/503、unknown/conflict/撤权等新表面的表现与可点击行为；记录为受控界面验证，不冒充真实模型或原安装异常注入。无自动POST、unknown无危险重试、cancelled保留既有效果。正式路径另取真实允许场景的证据，不为穷举修改用户登记。
7. **重登找回**：在静止的受测历史上退出并正式重登，不保留旧URL作为唯一发现手段；通过列表找到会话/Run/批准/结果，再刷新、回退、分页。网络与已有事实对照证明只读；不能将另一活跃Run自然推进算成历史GET副作用。
8. **结构与门禁**：既有测试保护精确字节、时间冻结、SSE事件聚合、同键继续/取消和身份隔离；新增测试只补目标映射、分页丢游标、迟到响应串Run等消费者可见风险。按仓库根入口运行构建/类型/行为和五CI门；不以目录、组件名、CSS类或静态文案断言凑覆盖。

### 7.3 证据与合同边界
