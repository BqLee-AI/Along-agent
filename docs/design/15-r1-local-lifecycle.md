# 15. R1 本地生命周期与配置复用

> 状态：Required；#67 行为合同，运行证据须独立取证。
> 范围：本机初始化、启停、显式升级、私有配置、持久数据和既有工作区登记加载。
> 不包含：开户/登录、选择管理员或新 owner 绑定、历史发现、视觉重构、R2、通用部署平台。
> 阶段：R1 日常可用性；#66 总跟踪，#67 独立验收，#68 消费稳定入口。

## 1. 依据与选择

[Observed] 根 package.json 提供依赖优先构建和开发入口；infra/compose/compose.yaml 编排 PG16 与 API/all，挂载 pgdata、workspace_data，未编排 Web。infra/docker/Dockerfile 构建正式 Linux x64 native 并打包 API/MCP。apps/web/package.json 有 Next build/start，Web 经同源代理访问 API。根 dev 不建立这套正式运行环境。

[Observed] scripts/db/apply.sh 按文件名执行全部 SQL，无旧库分流。0012 才建立 schema_migrations，0012–0016 各自记账；早期 SQL 不能重复初始化。API main 只在启动时加载工作区；workspaces/registry/service.ts 的登记缺失或读取失败均清空可用项。harness-config.ts 只接受显式模型配置，缺失时不启用 Harness。上述是静态代码依据，不是安装/升级演练。

[Required] 在现有 Bun scripts、Compose、正式镜像和 Next.js 生产 server 外补一层本机命令编排，不引入常驻管理服务、第二套 Agent 或配置 Web 平台。生命周期逻辑归 scripts/infra，业务事实仍归现有 TS 模块。Windows Web 与 Linux 容器分工保留；Web 进程仅承载生产页面和私有就绪标记，不作为管理 daemon。直接把 dev 或 apply.sh 包成启动命令无法满足持久配置、旧库和写者切换要求，不采用。

行为合同落在 local-lifecycle 能力；模块所有权见 [02 §1](02-modular-monolith-and-split-triggers.md)。工作区、Run 和工具规则继续沿用 [14 §3、§6、§7](14-r1-document-task-loop.md)，不重定义批准或恢复状态机。

## 2. 支持环境与固定入口

[Required] 支持 Windows 本机 Web（Bun 1.4.2、Next.js）与 Docker Linux x64 上的 PG16、API/all、正式仓颉和 TS MCP。Docker/Bun 可用性、必要端口和构建前置由入口检查，失败定位到依赖，不静默切换运行平台。发布端口只绑定 loopback；不把已有对外监听部署原样接入为受支持安装。

四个根入口均接受可选 --config <私有配置文件>，默认文件为 Windows 的 %LOCALAPPDATA%/Along-agent/local.json；选定后，启停与升级使用同一文件，不按仓库目录名重新推导安装身份。操作步骤见[本机使用指南](../guides/local-lifecycle.md)。

| 入口                  | 行为与完成条件                                                                                                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| bun run local:init    | 明确选择新安装或接入既有部署；建立/核对私有配置，准备依赖、正式镜像和 Web 构建。只在核实空应用库时应用全套迁移；不启动 API/worker 或开放任务。重复初始化只核对，不覆盖已有值。    |
| bun run local:start   | 复用配置及准备好的成套产物，核对库版本后启动 PG、API/all、Windows Web，报告可达入口和配置缺项。不安装依赖、不构建、不升级；缺产物指向初始化或显式升级。重复启动不增加第二组进程。 |
| bun run local:stop    | 停止本安装拥有的 Web、API/worker、native/MCP 子进程和 PG；保留配置、容器持久卷及资料。已停止返回无须操作；不按端口批量杀进程，不执行删卷操作。                                    |
| bun run local:upgrade | 明确准备目标源码对应的同批 TS/native/Web 产物；停旧写者后应用新增迁移，核验成功再启动新写者。无新增迁移不重放已记账 SQL；失败非零并说明所处阶段。                                 |

端口占用但不属于本安装时，start 失败，不换端口、不停止占用者。运行记录只保存识别本入口进程所需的非秘密信息；停止前核对进程身份，不能仅凭可复用 PID 或端口判断归属。接入原部署需要明确核对容器、卷、Web 进程和监听；无法证明归属时给出人工停写步骤，不接管或停止未知进程。

关闭终端或 launcher 意外退出不能触发业务重放。stop 会中断活动连接，不能承诺当前任务完成或回滚已经发生的文件效果；用户需先结束或明确停止任务。再次 start 不自动 resume Run、不提交消息/批准、不重写 unknown。既有 worker 恢复持久调度命令仍遵守原回执/取消合同，不把“不自动恢复 Agent”误解为禁用正常调度。

## 3. 私有配置、持久对象与 #68 接口

[Required] 配置使用独立于 checkout 的私有 JSON 文件，限制为当前本机用户可读写；代码、日志、PR 和普通状态输出均不包含秘密值。通过受控本机输入建立敏感值，不要求把 secret 放在命令行参数中。配置保存失败保留旧文件，不留下被误认为有效的半份配置；更新以同目录替换完整文件完成。实现复用既有环境变量加载器，不新建 provider 配置 API。

配置唯一保存以下用途所需的值或私有文件引用，具体 JSON 字段随实现保持这些边界：

- 固定 Compose 项目、明确的 PG/workspace 卷引用和工作区容器挂载位置；新安装固定一次，接入旧安装引用原对象，不因重命名 checkout 创建替代卷。
- 数据库连接、原 BETTER_AUTH_SECRET、旧部署已授权 HARNESS_MODEL_BASE_URL/HARNESS_MODEL/HARNESS_MODEL_API_KEY、TZDB_VERSION 和既有预算均保留，不因缺失默选另一服务。新安装可以明确暂缺模型。拟议用户模型切换时旧配置仅由管理员明确指定目标用户导入，不自动启用或共享，见 [design/22](22-model-provider-settings.md)。
- 固定 Web origin、Web/API/DB loopback 端口与 API_BASE；为后续认证提供同一个 APP_ORIGIN，避免 Web 地址与服务端信任来源分叉。
- 既有 WORKSPACE_REGISTRY_FILE 及受管资料位置。登记中的 owner_id、workspace_id、root、有限路径和权限规则沿用 design/14，不建立第二份 owner/授权事实。

新安装仅在确认没有原安装时创建新的认证密钥和存储对象。接入已有部署，缺原密钥、数据库/卷引用或登记来源时停止接入并要求恢复原材料；不从日志、浏览器或数据库推测秘密，不生成替代值继续。已有有效配置不得被 shell 中偶然存在的同名变量覆盖；生命周期入口只向相关子进程传递选定配置，不读取或写入仓库 .env 文件。

工作区资料准备只创建新安装的专用目录或装入明确授权的资料；不覆盖原登记和现存文件。仅有卷不表示资料已授权。原 root 必须保留物理身份；不得通过复制目录、重建卷或重建 root 来“修复”重启。既有登记读取失败、根身份/权限无效与未配置应有不同的本机诊断；不打印真实 owner 或宿主路径。失败项不开放，原无工作区业务与 healthz 仍按既有合同运行。

#67 提供同一私有配置的读取/保存入口、受管目录准备和按安装范围重载 API 的生命周期操作；重载复用 stop/start 的归属检查，不新增业务恢复入口。#68 在用户完成明确授权的开户/原账户转正后，决定唯一管理员，通过该配置入口保存登记位置并写入该管理员的登记，再调用必要重载。#68 拥有 owner 绑定和收尾失败反馈；#67 不选用户、不从多个 seed 中默取一个、不新建替代身份、不批量改 owner。具体内部函数名不作为对业务调用方的公开合同。

无账户/无登记的新安装可启动，输出“账户尚未配置”“工作区尚未配置”；不能调用 seed 补齐或宣称完整 R1 可用。账户状态由 identity 的公共读取负责，#67 不直查业务私表、不建安装管理员表；在 #68 提供正式状态前明确报告“账户状态未核验”，不把服务启动推断为已开户。#67 关闭不依赖 #68。

## 4. 数据库分类与初始化

[Required] PG 是事实源，私有文件只选择安装，不替代 schema_migrations。连接失败不是空库；版本最大值、某张表存在或手写配置标签不能独立证明完整基线。

| 检查结果                                              | 允许动作                                                                                                                               |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 新安装且应用 schema 经核实为空                        | init 在没有 API/worker 写者时按序应用原 0001–0016 及后续已发布迁移；每步失败即停。保持旧 SQL 原样，不给 0001–0011 补版本行。           |
| 既有、核实完整的 0016 基线（或随后受支持版本）        | 核对 0012 起完整连续账本与该版本必需表、列、约束、索引和触发器；start 只检查，不执行 DDL。upgrade 仅应用账本之后、满足前置的新增迁移。 |
| 未知/部分旧库、账本缺项、结构不符或版本高于所运行产物 | 拒绝启动写者和自动迁移，返回脱敏原因及维护步骤；不猜版本、不自动 stamp、不重放全量、不清库、不降级运行。                               |

实现需把基线检查与原迁移对应，并用真实 PG 保护“伪造最后一行/缺早期结构仍被拒绝”的边界；不预建通用 schema diff 平台。运行目标代码与数据库须兼容，普通 start 不能顺手升级旧库。早期初始化失败后的部分库归第三类，即使没有用户数据也不自动清空；维护者先备份、核对完成的 DDL/账本，再采取明确修复。未知前态不纳入自动升级支持范围。

## 5. 升级写者、失败与恢复

[Required] 同一安装的 init/start/stop/upgrade/重载互斥，避免 upgrade 停写期间另一 start 拉起写者；同一数据库的迁移持有独占部署许可，不能只依赖每个 SQL 内的账本锁。实现使用本机安装级互斥和 PG 会话级 advisory lock 覆盖迁移、校验至新写者交接；失去许可不得继续迁移或拉起写者。数据库锁只协调这些受支持入口，不声称可以阻止任意旧手工进程。

升级顺序：核对配置和目标产物，取得许可，识别并停旧 API/all/worker 与 Web、确认在途 native/MCP 不再写入，备份数据库与受管文件并确认可恢复位置，核对前态，事务性应用新增迁移并逐项核账，校验目标版本，启动同批 TS/native/Web。PG 在迁移期间可运行，旧 API/worker 不得由 restart 策略自行复活。发现不归本入口管理的写者或无法确认停写时中止升级，要求明确停写，不强杀未知服务。

迁移失败保留原数据、配置、原卷和可核对的逐步账本，不启动新旧业务写者。已提交步骤不重复执行；未提交步骤按该迁移的事务结果修复后显式重试，未知提交结果先从新连接核对，不盲重放。进程意外退出后，不凭残留 PID/标记推断升级完成；下一次 start 仍校验结构/版本及同批产物，未满足则要求显式 upgrade 处理。未完成升级时保持写者停止，不把健康 PG 当恢复完成。

目标程序启动失败也报告失败，保持停止或受控停写，不偷偷拉回旧版本。接受新调用、批准或文件效果后只能停写前滚，不恢复不理解新事实的旧写者。备份是维护恢复材料，不是自动回滚用户新事实的许可；不设计删除账本、重置 unknown 或重放活跃 Run 的修复方法。

## 6. 状态、指南与证明边界

[Required] init/start/upgrade 的输出独立报告进程是否可达、配置是否齐备及哪些能力未核验；错误说明下一步而不回显连接串、Cookie、key、私有端点、owner 或运行 ID。保留 /healthz 存活、/readyz 实际 TZDB/DB 连通的原语义，不把它们扩成账户/模型/工作区全局门，也不以 200 证明 schema 或资料任务可用。

模型配置存在、binary 可执行、MCP 能启动分别是前置，不是模型请求成功；日常 start 不自动发付费探测或修改资料。真实模型可用性只有明确执行的调用才记为验证，记录使用版本与范围。#67 真实路径验证覆盖 Web/API/native/MCP/PG/模型可达并保留原安全边界，但不重复 #62 全部任务变体，也不依赖 #68 才能证明生命周期。可在隔离既有身份安装上验证，seed/受控模型只能作夹具，不能成为用户日常启动或登录依赖。

实现指南必须覆盖新安装、原部署接入、配置恢复、四条日常命令、缺配置、端口冲突、未知库、升级中断/失败和保留数据。不得把旧 compose-smoke 的全新测试卷清理步骤复制进日常停止指南。指南区分仅服务启动与完整任务使用；开户转正指向 #68，历史和全站体验分别归 #69/#70。
