# 20. 本人目标内委托与授权

> 状态：Proposed；#105 的目标合同，不启用运行权限。
> 范围：设置、提醒、有限受管资料的自主步骤、可信事实、接续、结果、停止及新旧 profile 迁移。
> 不包含：业务实现、数据库迁移文件、部署、真实用户任务或后续议题创建；市场、模型供应商、推送与计费仍见 PRD 04 Deferred。
> 阶段：#104 能力重构；行为增量见 [OpenSpec change](../../openspec/changes/refactor-assistant-capability-authorization/proposal.md)。

## 1. 裁决与生效边界

[Required 目标] 用户委托目标，助理自主完成其中正常步骤；不是用户逐个批准工具。本人默认时区保存/清除、明确提醒创建/取消、受管资料查找/创建/修改/回读，不因写入、步骤多或对象多再次索权。明确要求的重写、覆盖、取消，在对象和影响唯一时不重复询问同一授权。

[Observed] 代码基线为 #103 合并后的 `4571b3b`；现行工具、批准、时间、单工作区和断流语义见 design/04/05/06/09/14。规划输入为 [重构方案](../demo/agent-capability-refactor-plan.md)，其建议不是已部署权限。#91/#102、#92/#103 已交付的交互与日期来源复用，不重新实施。

[Proposed] 新 Run 接纳时冻结 `authorization_revision=delegation/1` 和实际能力 profile。无该修订的旧 Run、business 提醒路径及旧 pending 均为 legacy：仍按原按钮、hash、有效期、单 grant、等待/恢复和连接合同执行。wire 版本不等于授权版本；不能让所有运行因换新 native 自动扩权。本文目标取代的仅是逐项批准策略、必选资料入口等明确列出的策略，不取消其他安全不变量。实施按完整用户切片逐步交付，未交付工具不得进入 profile；无能力时如实说明，不模拟执行。合并规范本身不接纳新 profile。

授权修订、实际能力和执行生命周期是独立事实：`delegation/1` 只定义目标内自主策略，不证明后台执行已交付。每个新 Run 同时冻结 `execution_lifecycle:'request-bound'|'server-owned'`，由 conversations 持有，并经可信 start、Run 只读投影和 Web 如实呈现。早期设置等完整切片可以采用 request-bound，沿现行请求绑定的断连取消语义，不承诺离开/退出后继续；仅在 §8 所有权与故障验收完成后，新接纳的相应 Run 才可冻结 server-owned。已接纳 Run（包括早期 delegation/1）不随部署升级、当前开关或批准恢复改变生命周期；缺此字段的 legacy 仍沿原合同读取，不回填。这里只增加两种具体生命周期，不建立通用 profile/权限平台。最终重构必须完成 server-owned 订阅解耦及其真实验收，不能以 request-bound 阶段替代收口。

身份/引用 ID 或 hash 证明归属和内容绑定，不证明“这句话授权了这件事”。模型误解和资料诱导仍有残余风险；不以第二模型 yes、关键词权限表或自然语言权限 DSL 伪装确定性授权证明。

## 3. 自主、澄清、授权升级与硬拒绝

| 情形                                                              | 行为                                                                                           |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 明确保存/清除本人默认时区；创建唯一明确提醒；取消唯一匹配本人任务 | 直接执行并返回已接受真实结果，不生成假 pending/consumed                                        |
| 明确取消所有未来提醒                                              | 完整分页定位相应集合，逐项执行并报告部分结果；不因数量重问，不承诺全局原子性或覆盖读取后新增项 |
| 受管资料检索、生成、保存、精确修改；用户明确要求整篇重写          | 在委托及登记内自主完成，保留版本/目标绑定；不逐文件审批                                        |
| 已证实零写的版本冲突；非固定文件名创建撞名                        | 可重新读取、计算或选不覆盖的名字并报告；原调用事实不改，不能沿旧精确许可写新目标               |
| 时间、目标指代、目的位置缺关键值或事实冲突                        | 只问会改变结果的缺口；模型先自行检索消除可查缺口，不要求用户抄内部 ID                          |
| 新业务目标、扩大资源或未授权破坏性影响                            | 说明具体新增影响，只请求该部分授权；原已授权部分不重新审批                                     |
| 跨 owner、登记外、链接绕过、不存在能力                            | 硬拒绝或明确不可用；按钮不能创造资格，不探测全盘                                               |
| 明确拒绝、停止、预算耗尽、硬权限失败或 unknown                    | 停止该 Run 后续动作；不改参数、换身份或自建 Run 绕过                                           |

资料正文只能提供事实。“只摘要这份文档”：即使文档要求保存时区、取消提醒，也只摘要，不执行注入动作。“按这些资料为明确截止事项建提醒”：允许使用资料事项/日期，在本人委托内直接建提醒；文档内无关取消/设置指令仍不获权。资料中相对日期缺文档时间语境时只问日期缺口，不能自动套用本次“明天”。

用户明确要求固定目标位置且现有内容会被覆盖时：若已明确授权该对象的覆盖则直接执行；若覆盖的是未授权无关对象，询问该具体影响。无法提供跨文件/PG 全或无时，用户要求全或无必须在首个副作用前说明，不靠事后补偿假装事务。

新 profile 对真实新增影响提供一次明确、范围精确的“授权并继续”用户动作：用户审阅被冻结的对象/影响（文件含完整目标、所见正文/hash）后，该动作可保存授权决议并显式请求继续原 Run 的对应有效等待点，不再机械要求第二个继续按钮。授权决议自身仍只授权，不执行领域写入、不证明文件保存；后续动作仍由同一 Harness 选择并通过当前 Run/attempt、原等待点、稳定调用、停止、预算及冻结生命周期门。可复用现有决议与显式继续请求，不预设 HTTP 请求数量、不新增自动恢复平台；legacy 仍保持原类型的精确审阅与显式继续合同，不将“显式继续”武断等同为既有界面必须两次点击。

拒绝、停止/终结、unknown、预算耗尽、失去资格或等待点尚未有效时不得推进；迟到授权即使留下真实决议，也不能复活 Run、预约新动作或变成稍后自动恢复命令。GET、导航、刷新、重登均不能授权/继续；按钮不能扩张冻结资源资格或自动批准其他影响。以上对两种冻结生命周期均适用；若 request-bound 已因断连失去原执行资格，一次动作也不能绕过该门。

## 4. 可信执行上下文和时间

[Proposed 接口] 使用 `harness/v6` 新 start 的 `TrustedExecutionContext`，由 TS 从认证和持久事实生成：

- `version:1`、`authorization_revision:'delegation/1'`、`input_message_id`；
- §1 的冻结 `execution_lifecycle`，不能从授权修订或当前部署推断；
- `received_at_utc`、`request_anchor_utc`；可信澄清关系 `continuation`（原 Run 及可空调用引用）；
- `timezone` 为可空的规范 ID、来源种类及可核对引用；
- `time_capabilities` 的 `elapsed_revision` 为可空真实计算修订，未交付即 null；`wall_rules` 为可空的实际 ruleset/tzdb/alias 身份；
- `workspaces` 为冻结登记资格的安全摘要集合，不包含秘密或宿主 root。

同一可信上下文进入模型的 system 层；用户原话和 MCP 正文仍为资料，不伪装成 system。工具时间输入为 elapsed/calendar_relative/wall 判别联合，保留原时间表达、独立事项和源引用。`FactRef` 只可指本轮 user message 或已接受观察；跨 Run 事实须经 §5 核验后带入。不得接受模型直接给定 `fire_at_utc`。

冻结事实只描述已交付且本 Run 可用的能力。只有偏好保存可用时，工具目录不暴露尚未交付的提醒/文件创建；已有工具也不能靠未实施的操作分支扩大能力。elapsed 未交付则无可用计算修订，有限创建未交付则无输出目录创建资格，缺省旧事实只表示不可用，不能编造版本或把未来工具/目录/后台承诺注入模型。能力随后上线也只进入新接纳的相应 Run；既有 Run 继续原冻结事实及当前撤权检查。

### 4.1 时区事实与优先级

本次明确时区 > 同委托刚接受且适用于该动作的设置回执 > 接纳时真实保存偏好。初始会话时区不能压过后来的明确设置；同轮新设置只影响后续尚未冻结动作。冲突且不能明确解释适用范围时只问冲突，不按首项选。

“先记住上海时区，再按它建明天下午三点提醒”可使用真实保存回执直接创建。“只这次按纽约”不保存默认值；清除后不能继续冒用被清除偏好。旧 task/approval 与接纳事实不修改，恢复不拿当前偏好重新解释旧动作。只支持真实规则包范围，不宣称完整 IANA。

### 4.2 严格 elapsed 与墙上时间

严格秒、分、小时及其明确组合由可信 UTC 请求锚加确定秒数计算，零时钟/env/网络依赖；不问时区或上午下午，不猜地理位置。“明天”“一个月后”“工作日”属日历语义，不当固定秒数。绝对/日历时间仍需要年份、日期、时段、适用时区及真实规则/DST；已给足或有可信依据的不重复问。“左右/尽快/有空时”仍挡回唯一时刻缺口。

严格 elapsed 无可用本地规则且用户未指定必须本地呈现时，冻结 UTC、offset=0、fold=0 与秒精度，不把 UTC 保存为本人时区。有真实时区及可用规则才冻结本地显示；明确要求某时区而规则不可用时准确说明，不伪造转换。纯 UTC 分支可不依赖 TZDB；`/readyz` 的既有规则故障仍如实非就绪，不伪报健康，也不把它当所有能力都不可用。legacy/business 的既有入站规则预检及零新 Run 保留；新自然目标在接纳时冻结实际可用时间能力，不要求 TS 在 SSE 前分类整句语义。实际工具确定类型后，wall 必须真实规则，严格 elapsed 才能走独立 UTC 分支；缺规则的 wall 动作零效果，已接纳混合目标保留先前真实成果。不用未知类型/猜测分支绕过认证、幂等或动作规则门。

提交前由 DB 当前时间校验原目标仍在未来；处理或补缺口导致过窗必须未创建，不悄悄换成“现在再加同样时长”。用户明确新的“从现在起”才建新锚。日历相对日期沿 #103 的请求锚/真实本地午夜边界，不因只过60秒重问，也不在跨日时静默顺延。

### 4.3 存储、API 和今日投影同交付

tasks 增加可空 `time_basis` 保存 elapsed 的可信锚、解析秒数、来源及计算修订，wall 分支保留实际规则身份；旧记录不回填。直接创建保存真实 `source_invocation_id`，旧 `source_approval_id` 保留；不得伪造批准来源。两条新旧来源路径各自受约束，不把所有来源字段同时放空当直接创建。

wall_time/timezone_id/fold/offset 保持非空。仅有对应 elapsed 依据且 UTC/offset0/fold0 的严格 UTC 分支允许 tzdb_version 空；其他分支继续要求真实规则身份，不伪造版本或全面 nullable。新展示有独立版本并冻结秒精度；不改旧模板/hash。

任务列表/详情/通知与 Web 消费者同步识别新来源/时间依据。今日只读投影按明确浏览时区（偏好，否则明示 UTC）计算服务端 UTC 日区间，按 fire_at_utc 取记录；卡片只显示各自冻结字段，不在前端转换历史。UTC 提醒与跨冻结时区任务不得被旧“相同时区+本地日期”过滤漏掉。查询区间计算不改写展示，GET 不产生业务效果。

## 5. 澄清与接续：复用可信跨 Run 来源

复用 conversations 的 #103 来源核验责任，不找“最近任意 Run”，不新增 suspended_input、输入长等待、snapshot3、目标表或可执行 DAG。

新缺口（time/timezone/target_selection/destination）须来自已接受工具结果，或前序 Run 原子保存的结构化目标结果；没有调用不伪造 invocation。接纳事务核对同 owner/conversation、真实原消息、允许的前序终态、实际未解决缺口、唯一且紧邻关系和未被接续。多候选、无关中间目标、无可靠旧来源或新目标不能继承；只问实际关系缺口，不强迫重批全部目标。沿现有 conversations 行接纳锁，在同一事务复验前序终态/无后继并保存唯一关系，防并发两个续办；若需要锁 Run，保持现有 attempt→Run 锁序，不改旧上下文和结果，不另造先查后写协议。

接续带入已接受收据及未完成部分，计入上下文预算；不把旧观察当新读取或重做已完成任务/文件。用户明确新请求即使文字相同也可创建新任务，不按相似度合并。每 Run 保留冻结预算；同 Run 批准恢复累计；明确用户补充创建的新 Run 使用新预算，不承诺跨目标总费用硬上限。系统不得自动开 Run 绕预算。

## 6. 领域提交、稳定调用与真实结果

### 6.1 事务型能力

[Proposed] TS 工具目录由 tools 单一显式定义生成：`get_user_prefs/set_user_timezone`、`list_tasks/get_task/create_reminder/cancel_reminder`、`read_brief_cards`、有限 workspace 工具及原观察回取。不接受 owner、SQL、root 或替用户确认参数；risk 只是描述，不是授权引擎。

创建归 tasks 公共 `createTaskWithinTransaction`：task、task_events.created、schedule outbox 一次提交；新调用的 accepted result/审计同事务。legacy confirm 完成 owner/pending/时限/hash 校验后调用同一用例再 consumed，失败全回滚。取消复用 tasks 公共事务，偏好写入归 identity 并与接受结果原子提交。不复制 approvals 私有创建 SQL，不由 conversations 直读 tools 私表。

取消从 cancel_pending 提交计时，取消优先；无排期回执不 scheduled，无撤销回执不 cancelled。created 不等于已排期/到点/通知送达。task_events/审计只追加，唯一约束、GET 零业务写入和冻结展示不变。保存的简报是 workspace 文件，`/brief` 仍为 tasks/approvals 只读投影，不新增 briefs/cards 表。

### 6.2 去重承诺的边界

在既有入站幂等有效窗口内同键重放原 Run；同稳定 invocation/call key 重放原接受结果，同键异参冲突；已接受结果不可覆写。现行入站键为24小时有效，过期再提交不承诺返回原 Run，客户端仍不得自动补发；不把它与 task 批准期限、无统一TTL的文档批准混同。未知不得换 slot、引用或新 Run 重试。新明确委托和明确要求两条相同提醒不能按 args hash 吞并。

不新增模型发号的 item_key/effect_key/supersedes 持久层；模型可能把语义旧动作误判成新动作，稳定调用不消除此风险。不承诺任意自然语言 exactly-once。接续先核既成收据并只做缺口，真实模型评估重复与漏目标；只有可复现事故及模型外稳定业务身份的证据才重开去重设计。

### 6.3 目标结果不是 Run done

[Proposed 接口] 同一 Harness 增加 `finish_goal` 控制出口，不是业务工具或新执行器。GoalResult 包含 `status:completed|partial|blocked|cancelled|unknown`、逐项目标 outcomes（achieved/not_done/blocked/unknown）、receipt_refs、可空 typed clarification 及可见 answer。TS 校验收据 owner/来源/类型和实际领域事实，将目标结果、最终消息、唯一 Run/attempt 终结和事件原子保存。

- completed：列明目标均有相应完成证据；纯回答可无效果。创建提醒的目标可由真实 created 达成，但不能说已排期/已提醒。
- partial：部分达成，其余未做或阻塞，列明事实和缺口；没有达成项的缺信息是 blocked。
- unknown：任一要求的效果不确定时保留未知并停止，不用 partial/completed 掩盖；明确停止记 cancelled，并逐项保留已发生/未知效果。
- Run 执行结束、工具 completed、pending 提议或模型正文均不等于目标完成。预算/失败终结也须给出真实已完成/未做/未知项，不伪造成功结果。

文件完成要求真实写入接受后独立新全文 read，只有 applied 不报 verified。已接受旧观察回取不满足新回读。模型仍负责列出自然语言目标，TS 只能阻止伪造证据、掩盖已知未决，不能证明模型未漏目标。

## 7. 工作区资格、有限创建与精确写入

部署 workspaces 登记 owner、digest、root identity、有限 readable/writable_paths；新增有限 output directories 只用于普通文件创建，不授权任意 mkdir/move/delete。新 Run 冻结本人可用登记资格集合，用户明确选更窄范围时只冻结该子集；模型见友好摘要并在集合内选择 workspace ID，TS 解析实际 grant。不要求先切资料模式，不默认第一项；对象/位置确有多个合理答案才问。

无登记明确不可用；登记新增/变化不进入旧 Run，新动作仍验当前摘要和资格。集合超过帧/上下文容量时明确限制，不把静默截断当完整权限事实。工具可见性、部署资源资格与本次语义委托三者独立，任一不足不能靠按钮放行。

直接编辑从本 Run 已接受的完整读取编译精确对象、基线、目标字节并绑定 invocation，不创建自动 approved 文档单。正常修改保留无关字节；明确整篇重写以全文目标绑定，允许改变用户明确要求改变的内容。版本 CAS、可信目录/路径身份、锁与真实发布保留。确定零写 conflict 可新读重算；旧精确许可不重用，拒绝/未尝试/unknown 不能冒充零写后继。

创建在冻结输出目录内 no-replace 原子发布，撞名不覆盖；用户未固定名时可选不覆盖别名，固定名所需新影响按 §3 裁决。采用同文件系统独占链接发布并移除临时名、核对目标 nlink=1 等真实排他机制；普通覆盖 rename 不满足创建。文件系统不满足前提就明确不可用，不降级覆盖。编辑沿既有临时文件/rename/fsync 边界。部署登记与协作写者是保证前提，PG 锁不是任意宿主进程的 OS 沙箱。

非事务一次许可前先持久 unknown；只有确认取得许可的当前执行栈可实施，accepted result 归 tools。写后独立新 read 才可 verified。响应/接受结果丢失且无绑定证据时保持 unknown，即使当前内容相同也不补造成功、不再写；可只报告当前字节事实。真实新增影响需要精确预览与授权；legacy 文档批准继续冻结所见内容/hash、唯一 apply 和显式同 Run 恢复，不能把它自然升级为直接写。

## 8. 连接、停止、退出与服务端所有权

以下表格与 driver 要求仅适用于冻结 `server-owned` 的新 Run。`request-bound` 的早期新委托和 legacy 仍按各自原连接/等待合同收尾；断连可能取消执行，但不能回滚已接受偏好/任务/文件，也不能通过重连自动重做。UI 在接纳和历史读取中显示真实生命周期，不把“可自主保存偏好”显示为“后台执行已上线”。

| 动作                       | server-owned 的可观察语义                                                           |
| -------------------------- | ----------------------------------------------------------------------------------- |
| 离开/刷新/断网             | SSE 断订阅，不撤销已接纳委托；同一执行在原预算/超时内继续                           |
| 重连/历史 GET              | 只补读持久事实，不发消息/确认/恢复/取消或新建 attempt                               |
| 显式停止当前 Run           | 先持久撤销后续动作资格，再 abort native/transport；保留已发生和在途未知效果，不回滚 |
| 取消已建任务               | 单独明确目标，走 tasks 取消事务/回执门，不由停止隐式代做                            |
| 退出登录/会话到期          | 服务端确认会话撤销或到期，断开访问；不撤销原已接纳委托，重登只读                    |
| 账户 disabled/明确资源撤权 | 拒绝新动作；既成事实保留，返回时不披露已撤权内容                                    |

[Proposed · server-owned] 薄 run-driver 持有同一 executeHarness、AbortController 和执行生命周期，不编排业务目标。沿 Run/attempt gate 用专用 PG session advisory lock 取得同 Run 唯一占有，将锁连接身份与 attempt 绑定；在预约、非事务效果许可和终结核验占有仍有效，不能只等进程失联回调。失联立即 abort，资格丢失后禁止新动作；已获许可的在途非事务效果如实收尾为已知/unknown，不承诺把在途 IO 撤回。

后继处理者只有取得同锁并复验后才将遗留 running 终结为中断，不重放工具/模型；不永久假报 running，不承诺崩溃自动恢复。锁连接与现有池/并发容量有界；保持每 Run 预算及供应商超时，不引入无限运行时长或通用租约平台。只删除 request abort 回调不足以交付 server-owned。legacy 和先前 request-bound Run 不在升级或恢复时悄悄改后台语义。

## 9. 协议、历史与前向迁移

新 start/finish 在 TS/native/Web 同批显式升级到 v6，外部新结果为 SSE v2；旧 v1 事件保持可读，严格旧消费者不接新 shape，不在 v5 暗塞字段。现有 v5 native 对未知协议硬拒绝；不能用旧二进制作为 v6 执行器。snapshot 继续 v2，GoalResult 只在终结持久化，不造 snapshot3；legacy snapshot1 仍限原无 workspace/旧业务引用规则。

TS 对可恢复 legacy 采用显式 profile 到新 wire 的受限适配：原 allowlist、单 grant、冻结时间、原批准/结果、snapshot 引用及累计预算不变。适配只读历史，不回写快照，不向新调用方保留旧工具别名；新调用方完整迁往目标工具。不能安全适配的有效旧等待在发布前安排续完或明确停止，不升级后才遗弃；文档批准没有 task 的统一24小时 TTL，不能等一天假装全部过期。新委托不自动消费旧 pending，新 profile 不迁写旧 Run/批准/模板/hash/accepted result。

仅新增前向 migration：identity 偏好由原字段用例管理；tasks 来源/时间依据及约束归 tasks；Run 上下文/结果/接续/执行占有归 conversations；登记格式/输出目录与效果归 workspaces；tools 继续唯一 accepted result。任务/今日 API、SSE/shared contracts 与 Web 同步，未实施字段不成为当前 API 保证。

发布：核对旧有效运行及产品安装归属 → 停旧写者 → 前向迁移 → 配套 API/native/Web → 核验协议/能力身份 → 才接纳新 profile。新事实产生后不回退到不理解新授权/时间/直接来源的旧写者；关闭新入站、保留事实、前向修复，不承诺无损 down migration。#100 安装/资产冻结不动，#101 不运行，不新建第三套安装。
