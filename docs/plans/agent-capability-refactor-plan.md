# 助理能力与授权模型重构方案

> 状态：Proposed；本文件提出目标合同、技术取舍与实施顺序，不启用新的运行权限。
> 范围：可信上下文、业务与工作区能力、目标内自主执行、必要澄清、效果与停止、历史兼容。
> 不包含：本轮业务实现、部署升级、真实用户任务操作、任意宿主访问或新的外部通道。

> 合同入口：[#104](https://github.com/BqLee-AI/Along-agent/issues/104) 定总路线，#105 首阶段见 [design/20](../design/20-goal-scoped-delegation.md) 与 [OpenSpec 归档](../../openspec/changes/archive/2026-11-12-refactor-assistant-capability-authorization/)。本输入保留 Proposed，详细字段/状态/迁移以 design/20 为单一真源；§11 的 A–F 是技术责任分组，不是授权自动创建的 Issue 批次。九步交付沿 #104 逐阶段建立，明确提醒复用 #90。

## 1. 结论：让助理完成委托，而不是管理一串审批

推荐把执行模型从“模型只能提议，写入逐项批准”改成：**用户委托目标，助理自主选择正常步骤，服务端约束真实资源并可靠提交，结果依据实际效果。**

本人设置保存、明确提醒创建、唯一目标取消，以及受管资料的正常创建和修改，在委托范围内直接执行。不因“这是写操作”“有好几步”“涉及多条提醒”而额外要求用户点头。只在缺少会改变结果的信息、需要扩大委托或承担尚未授权的实际影响时打断；已明确要求的覆盖、重写、取消不重复询问相同授权。

这次不是只给现有工具补几个问法，也不是只去掉创建按钮。目标是使一次“按这些资料整理简报、保存结果，并提醒其中明确截止的事项”真正走完检索、判断、写入、建任务、核实和汇总。用户不必替助理选择工具、复制任务 ID、换算时钟或逐步点继续。

保留唯一仓颉 Harness、TS 业务能力层、Postgres 事实源及既有可靠提交机制。不引入第二套 Agent、通用权限 DSL、工作流引擎、第二个语义裁判、全局自主模式开关或新的数据库。

## 3. 什么可以自主做，什么才需要问

一次委托约束的是目标与影响范围，不是一份不可变工具调用清单。模型可以更换检索顺序、重复读取、修正确定零写的冲突、先完成独立部分，不需要用户批准这些正常步骤。

| 情形                                                             | 建议行为                                                                     |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| “记住我的默认时区为上海”或明确清除本人默认时区                   | 直接保存、返回真实值；不是任意账户字段修改                                   |
| 明确、可唯一确定的本人提醒创建或取消                             | 直接提交，不再问“是否真的执行”                                               |
| “取消我所有未来的提醒”                                           | 完整分页定位后执行，逐项报告；不因数量多机械重问，不声称全局原子取消         |
| 获委托资料任务中的查找、读取、生成、保存、精确修改和回读         | 在已登记资格内自主执行，不逐文件审批                                         |
| 用户明确要求重写指定可写文档                                     | 直接执行，保留真实版本与无关字节约束；不能只因整篇重写再索取一次授权         |
| 时间缺关键语义、两条任务都符合指代、资料日期冲突、目标位置不唯一 | 只问实际缺口；不让用户抄 UUID，不重问整个目标                                |
| 文件版本冲突且能证明零写                                         | 在原目标内自主重读并重新计算，不能沿用过期精确批准                           |
| 新建撞名但可选择别名且不改变用户目标                             | 自主选择不覆盖的目标并报告；若用户要求固定路径且会覆盖无关内容，才问具体影响 |
| 新增目标、扩大资源范围、尚未委托的破坏性替换                     | 明示新增影响，请求该部分授权，不重复审批已有部分                             |
| 跨 owner、登记外路径、链接绕过、不可用工具                       | 硬拒绝或如实说明缺能力；不能靠一个确认按钮突破部署资格                       |
| 拒绝、明确停止、预算耗尽或未知副作用                             | 停止相应执行；不换参数、换调用身份或自动新建 Run 绕过                        |

新增影响的具体交互以 [design/20 §3](../design/20-goal-scoped-delegation.md#3-自主澄清授权升级与硬拒绝) 为准：新profile允许一次精确“授权并继续”，决议自身不写领域/文件，原Run/有效等待点/资格/停止/预算继续约束，不机械要求第二按钮或预设HTTP次数。legacy保留原合同；拒绝、unknown或迟到失效不推进，GET/重登不触发，不扩冻结资源。

### 资料事实不是授权，但合法委托可以使用资料

“总结这份文档”不授权文档里写的“改默认时区、取消所有提醒”。“按文档里的事项建立提醒”则授权助理使用其中明确的事项和日期完成用户目标。前者应拒绝注入的额外动作，后者不应被“来源是第三方”一律挡住。

模型负责理解委托、指代、相关事实和实质歧义；服务端负责确定性证明身份、资源资格、引用归属、时间、调用、版本、停止资格与效果。消息 ID、来源引用、参数 hash 只能证明关联，不能证明自然语言语义。不开第二个模型裁判，不以权限关键词词表伪装解决这个问题。

残余风险是模型误解目标或被资料诱导。有限资源、真实结果、显式停止与真实模型正反例评估可以约束影响，不能宣称消除了语义越权。

## 4. 资源资格与委托分开，取消不必要的手动选择

工具目录表达“产品能做什么”；部署登记表达“哪些资源真实可达”；用户委托表达“这次为什么可以做”。三者不能互相替代。模型看见工具不等于任何时候都能使用，用户请求也不能创造不存在的能力。

工作区沿用登记的 owner、registration digest、root identity 和有限读写范围，不接受模型传 root。不再要求用户每次打开“资料”菜单、选登记后才可能调用文件工具：

- 接纳新 Run 时，由服务端冻结该 owner 可用的登记资格集合；用户若显式选择更窄范围，则冻结该范围，不扩大。
- 模型可见友好名称、用途和有限相对范围；在冻结集合内按目标选择工作区。工具只接收集合内的 workspace ID，由 TS 查对应 grant。多登记不是“默认选第一项”，确实有歧义才问。
- 初始事实可以包含多个现有 WorkspaceGrant，而不是让模型中途修改单个 grant。没有登记时如实说明，不探测全盘。登记新增/变更不静默进入旧 Run；需要重新接纳明确请求。
- 现有 writable_paths 继续约束既有文件；新增明确的受管输出目录集合用于新文件创建，只允许目录内的普通文件，不推导为任意 mkdir、移动或删除。
- 可用登记仍受既有上下文/帧预算约束；若不能完整表达资格，应类型化报告限制，不悄悄截断成权限事实。没有规模证据，不新建注册服务或权限缓存。

这会改变单 WorkspaceGrant 的启动、工具上下文和校验合同，需要同步迁移；收益是模型能够真正选择工具和资源，而不是让用户先替它完成分派。

## 5. 目标级能力与唯一所有者

采用由 TS tools 拥有的显式定义，复用现有 zod、read_only/local/non_transactional 分类和分派。输入、描述、验证和执行分类不能维护第二份不同目录。`risk` 只作描述，不能冒充授权引擎。

| 能力                                           | 语义及所有者                                                                                 |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `get_user_prefs`、`set_user_timezone`          | identity 读取、保存或清除本人默认时区；返回真实已存事实，不提供 users patch                  |
| `list_tasks`、`get_task`                       | tasks 提供稳定分页、完整事项与真实状态，使助理能定位而非猜测任务                             |
| `create_reminder`                              | tasks 的真实创建用例；时间归一后直接建任务，不是假提议或 consumed 假批准                     |
| `cancel_reminder`                              | 调用现有 tasks 取消事务；如实返回 cancel_pending 或已取回执的 cancelled                      |
| `read_brief_cards`                             | 只读聚合；不伪称生成的文档已存入简报表                                                       |
| `workspace_list/grep/read`                     | 真实 TS MCP 在冻结登记内读取，返回版本及不完整性                                             |
| `workspace_create_file`、`workspace_edit_file` | workspaces 拥有创建/精确修改、版本门、一次许可和真实效果；正常写不必先创建 document_approval |
| `read_run_observation`                         | 回取允许的旧事实；不能冒充新读取或保存后的独立核实                                           |

工具不接受 owner、任意 SQL、宿主 root 或“替用户确认”参数。模型侧自由决定调用序列；确定性服务端不增加一套自然语言工作流分诊。

“生成并保存简报”的真实产物是受管工作区文件；现有 `/brief` 仍是 tasks/approvals 的只读投影，不新建 briefs/cards 表。改期仍按明确取消旧项、创建新项的领域语义，不直接 UPDATE 冻结时间。

## 6. 可信上下文与时间语义

以下为建议接口，不是当前导出。新增 start 字段和结果语义使用 `harness/v6`；不借同一协议号偷偷改变严格键。

```ts
type FactRef =
  | { kind: 'user_message'; message_id: string }
  | { kind: 'accepted_observation'; invocation_id: string; field?: string };

type TrustedExecutionContext = {
  version: 1;
  authorization_revision: 'delegation/1';
  execution_lifecycle: 'request-bound' | 'server-owned';
  input_message_id: string;
  received_at_utc: string;
  request_anchor_utc: string;
  continuation: null | { source_run_id: string; source_invocation_id: string | null };
  timezone: null | {
    id: string;
    source: 'explicit_request' | 'saved_preference';
    source_ref: string;
  };
  time_capabilities: {
    elapsed_revision: string | null;
    wall_rules: null | { ruleset_id: string; tzdb_version: string; alias_version: string };
  };
  workspaces: WorkspaceSummary[];
};

type ReminderTime =
  | { kind: 'elapsed'; expression: string; source: FactRef }
  | {
      kind: 'calendar_relative' | 'wall';
      expression: string;
      source: FactRef;
      timezone?: string;
      fold_choice?: 'first' | 'second';
    };
```

TS 从认证、入站 DB 时刻、冻结日期来源、真实偏好和登记生成上下文。仓颉以可信系统上下文提供给模型，不伪装用户消息，不把资料正文提升为系统规则。语义源引用必须属于本 Run 或经核验的可用前序事实；引用本身仍不证明授权。

阶段能力与生命周期的唯一合同见 [design/20 §1、§4、§8](../design/20-goal-scoped-delegation.md)。授权修订不证明后台已交付；偏好等先交付可冻结并显示 request-bound，断连仍按请求绑定策略收尾。elapsed未实施即无修订，文件创建未实施即无对应工具/输出资格，不对模型编造能力；不预建未来profile。

### 6.1 时区与同一委托内的设置

新请求优先使用本次明确时区，再使用已保存偏好，不让会话初始时区永久压住后来明确设置。一次“先保存上海时区，再据此建立提醒”可引用刚接受的设置回执，影响后续尚未冻结的动作；不修改原接纳事实或既有 task/approval。

“只这次按纽约”不保存默认值；跨 Run 恢复不读取当前偏好来重新解释旧动作。支持范围以真实规则包为准，不因工具字段名是 timezone 就宣称支持完整 IANA。

### 6.2 三分钟后，不应再问上午下午或时区

严格经过时长由可信请求锚加确定秒数决定，不依赖用户本地时区。模型分类/提取，纯时间函数解析和计算；不接受模型直接给 fire_at_utc。“明天”“一个月后”“工作日”不能伪装成固定秒数，未知语法也不猜。

- elapsed 支持明确秒、分、小时及组合；纯 UTC 计算不依赖 TZDB。
- 有真实已知时区且规则可用时，服务端生成冻结本地显示。否则明确使用 UTC、offset 0、fold 0 和秒精度，不把 UTC 存成用户默认时区，也不冒充用户所在地。
- 用户明确要求某本地时区而规则不可用时，如实说明，不能伪造转换。墙上时间及日历相对时间仍走实际规则、DST 和必要澄清。
- 原目标因处理或澄清延迟已过，提交前按 DB 现在校验并返回未创建；不能悄悄改成“现在再加三分钟”。用户明确发出新的“从现在起”才产生新锚。
- 新请求/可信澄清/跨日来源复用 #103 的规则所有者；资料中的“明天”若缺文档时间语境，不能自动套成本次明天。
- legacy/business保留既有入站规则预检及零新Run；新自然目标冻结真实时间能力，实际工具分支才裁决wall/elapsed，不要求TS在SSE前语义分类整句。wall缺规则零该动作效果、保留混合目标已有成果，readyz仍准确非就绪，不能靠猜测绕规则门。

### 6.3 存储与展示必须一起修改

建议新 tasks 增加时间依据 `time_basis`：elapsed 记录真实 anchor、解析后的 duration_seconds、源引用及计算版本；墙上时间记录规则身份。旧记录不回填。直接创建增加 nullable 的 `source_invocation_id`，旧 source_approval_id 保留真实来源，不造批准。

wall_time、timezone_id、fold、offset 仍非空；严格 UTC elapsed 只在有对应依据且 UTC/offset0/fold0 同时成立时允许 tzdb_version 为空，其他新旧分支继续要求实际规则版本。新增迁移约束该分支，不伪造 TZDB 版本、不把全部字段改成 nullable。新回执冻结秒精度与展示版本；旧批准模板/hash 保持原样。

现有[今日查询](../../apps/api/src/modules/brief/repository.ts)按相同时区和 wall_time 日期筛选，会漏掉其他冻结时区及 UTC 提醒。建议按明确浏览时区（默认偏好，否则清楚标 UTC）计算只读 UTC 日区间，再按 fire_at_utc 查询；卡片仍显示自己的冻结字段，前端不换算历史。这些 tasks/brief DTO、详情、列表和投影要与 UTC 创建同批交付，不能等收口时才修。

## 7. 澄清接续和目标结果：不新增目标执行引擎

**Run 保持一次执行生命周期，目标结果独立表达。** 缺信息时当前执行可以结束，但目标是 blocked 或 partial，而非“事情已办完”。用户补充后，新 Run 通过可信前序关系继承适用锚和既成结果。

#103 已有提醒澄清来源核验，但不等于支持所有目标缺口。把新增任务选择、目的位置等 typed clarification 接入同一 conversations 来源核验责任：前序本人消息、可接受终态、真实未解决缺口、唯一关系、尚未被接续；来源引用不是自由传入一个 Run ID。缺口可来自已接受工具结果，或前序 Run 已原子保存的结构化目标结果；没有工具调用时不伪造 invocation。并发接续沿现有 conversations 行接纳锁，在同一事务复验来源及无后继再插入唯一关系，不改旧冻结上下文或结果；若需锁 Run 则保留现有 attempt→Run 锁序，不能仅靠先查后写制造两个后继。同入站键仅在既有有效保留窗口重放原响应。

保留每 Run 预算；同 Run 批准恢复仍累计。跨 Run 的明确用户补充沿用新 Run 预算，不宣称有跨目标总费用上限。系统不得自行创建新 Run 绕过预算。普通后续消息不是默认续办；目标或资源范围改变时重新接纳明确委托，不修改旧 frozen_context。

不增加 suspended_input、输入长等待、快照 v3、目标表、可执行 DAG 或完整计划数据库。旧批准等待仍按当前 checkpoint 同 Run 继续。

```ts
type GoalResult = {
  status: 'completed' | 'partial' | 'blocked' | 'cancelled' | 'unknown';
  outcomes: Array<{
    label: string;
    status: 'achieved' | 'not_done' | 'blocked' | 'unknown';
    receipt_refs: string[];
    reason?: string;
  }>;
  clarification: null | {
    kind: 'time' | 'timezone' | 'target_selection' | 'destination';
    source_invocation_id?: string;
    question: string;
  };
  answer: string;
};
```

建议增加同一 Harness 的 `finish_goal` 结构化控制出口，不是新的业务执行工具。TS 核验收据归属、类型和真实领域状态；文件完成必须有 apply 后独立新 read。把目标结果、最终消息和唯一终态原子保存，Web 用真实任务/文件卡分别展示，不拿 tool completed、pending proposal 或模型正文当成功。

模型仍负责列出用户目标，服务端无法证明模型没漏掉任何自然语言要求。结构化结果只能防止伪造收据和掩盖已知未决效果，不宣称完备的目标证明。纯回答可以没有效果；执行目标没有真实回执就不能出业务成功卡。

新 start/finish 同批升级 TS 与 native；SSE 新执行使用显式 v2 结果合同，旧 v1 事件保持可读，不向严格旧 shape 暗塞字段。snapshot 字段仍可保持 v2：目标结果在终结持久化，不为它复制整套快照。跨 Run 接续额外带入的既成收据要有明确来源且计入上下文预算，不把旧 observation 当新调用执行。

已知零效果错误可反馈模型修正，独立分支可继续并报告不完整；依赖该错误的步骤不能猜。拒绝、停止、预算耗尽、硬权限失败、unknown 停止。跨文件和 PG 没有全局事务，不自动撤销已成功任务来假装 all-or-nothing；用户明确要求全或无而能力不能保证时，在首个副作用前说明。

## 8. 可靠提交：复用现有身份，不新增模型发号的去重层

### 8.1 事务型业务

将任务写入从 approvals 私有仓库迁到 tasks 的 `createTaskWithinTransaction`：task、created、schedule outbox 由该用例负责。旧 confirm 完成原校验后调用它再 consumed；新工具通过现有本地调用事务调用它，业务事实、accepted result 与审计共同提交。取消和偏好写入也与各自接受结果原子提交。

新路径不模拟 confirm、不制造 consumed approval，也不复制创建 SQL。跨模块只通过公共用例/投影，conversations 不直读 tools 私有表。

### 8.2 幂等的确切承诺

复用入站键、稳定 invocation/call key、参数绑定和不可变结果：在既有24小时入站键有效窗口内同请求重放返回原 Run，过期再交不承诺原 Run 且客户端不能自动补发；同调用返回原接受结果，同键异参冲突；新明确请求即使文字相同也可以合法创建新任务。不将入站键期限与 task 批准期限、无统一 TTL 的文档批准混同。

不增加模型生成的 item_key、数据库 effect_key、通用 supersedes 或按参数 hash 合并语义动作。模型换个自报身份照样可能重复，它们不能产生任意目标 exactly-once；强行按内容合并还会吞掉用户明确要的两条相同提醒。

模型应先根据已接受收据核对既成事实，接续不重做已完成项。未知效果不能换新调用重试。语义上误判成“新动作”的重复仍是残余风险，需真实模型评估；只有出现可复现事故且找到模型之外的稳定业务身份，才重开额外去重设计。

### 8.3 工作区写入

直接写仍要从本 Run 的已接受全文读取编译精确对象、版本及目标字节，将冻结目标归属该 invocation，不创建“自动批准”的 document_approval。真实需要扩大影响的操作才生成精确预览并等待用户决议；旧批准继续保留其所见内容/hash。

编辑复用现有版本 CAS、可信路径/目录身份、互斥、临时写入、rename/fsync。创建使用受管输出目录和原子 no-replace 发布：例如同文件系统独占链接发布后移除临时名，再核对目标 nlink=1；不能用会覆盖目标的普通 rename 冒充 exclusive create。不支持该发布前提的文件系统应明确不可用，不能降级为覆盖。

非事务一次许可先持久记录 unknown，只有确认取得许可的执行栈实施效果；接受结果仍归 tool_invocations。真实写后独立新 read 才可 verified。接受结果丢失时，当前内容碰巧等于目标不证明本调用成功，不补造回执、不重写；可以报告当前内容事实，同时保持原效果 unknown。

这些保证依赖可信登记与协作写者，PG 锁不约束任意宿主进程，不宣称获得 OS 级文件沙箱。未知效果停止整个 Run；已发生事实和未知项分别保留。

## 9. 离开页面不等于撤销委托，停止也不是回滚

[Proposed · 最终 server-owned 切片] 冻结 server-owned 的新 Run 中，SSE 仅订阅事实；刷新、断网、离开页面不取消已接受执行。早期 delegation/1 可以冻结 request-bound，不承诺后台继续；两者都保留显式停止先撤后续资格、既成效果不回滚、取消任务为独立目标。只有 server-owned 的退出/到期不撤已接纳执行，request-bound 沿原连接策略；账户禁用拦住新动作。

现有执行由请求流持有，不能只删除 abort 回调就承诺后台运行。建议增加薄 run-driver，仅持有同一 executeHarness 的执行生命周期、AbortController 和唯一执行占有，不编排工具、不创建第二种任务。

沿用 Run/attempt gate，在 PG 中用 session advisory lock 确保同 Run 唯一执行者。领取时将锁连接身份与当前 attempt 绑定，每次预约、效果许可和终结都核验当前拥有者及锁仍有效，不能只依赖进程收到失联回调。锁连接失联立即 abort，资格失效后禁止发出新动作，在途非事务效果按已知/unknown 记录。另一进程仅在取得同锁并复验后，将遗留 running 终结为中断，不自动重放。执行拥有者绑定属于 E 切片的最小运行状态，不另建租约/恢复平台；连接数量受现有池与并发容量限制，不增加无限运行时长承诺。

离线继续不等于进程崩溃自动恢复：保留当前预算及供应商请求超时；宿主中断如实投影，不能长久假报 running。重连只 GET 补事件，不重发消息、确认、继续或取消。后台完整切片完成后仅新接纳的相应 Run 采用 server-owned；旧 Run 和先前 request-bound Run 保持冻结连接语义，不能被部署升级改义。最终重构仍须完成该切片及验收，不以早期阶段替代。

## 10. 历史、迁移和发布

新 Run 才冻结 `authorization_revision=delegation/1`。旧无该版本 Run 的 allowlist、grant、时间依据、批准模板及 accepted result 不迁写，不自动消费 pending。历史读取与允许的旧批准恢复仍保留旧能力，不借新 native 协议扩权。

新增 v6 writer/consumer 同批交付。旧 v5 native 对未知协议硬拒绝，不能把旧二进制当兼容执行器。TS 按冻结 profile 显式适配可恢复历史到新 wire：保留原允许工具、旧批准决议和快照引用，仍按旧授权规则执行；v1 快照继续受现有无 workspace/旧业务引用校验约束。该适配只服务既有数据，不向新调用方暴露旧工具别名，不写回历史快照或扩大资格。

旧有效等待若无法安全适配，应在发布前核对并明确安排其续完或停止，不能升级后才给用户一个无解释的不可恢复错误。文档批准没有任务批准的24小时 TTL，不能笼统以“等一天全部自然过期”处理。用户新委托也不能偷偷消费旧待批项。

新迁移只新增，不改已合并 migration。冻结字段/登记集合、直接创建来源、UTC 时间分支、目标结果与 SSE 版本均须有明确 schema 所有者；查询只读兼容空的新字段，不伪回填历史授权。

发布顺序：核对产品安装和旧有效运行 → 停止旧写者 → 前向迁移 → 配套部署 API/native/Web → 验证协议/能力身份 → 接纳新 profile。新写入发生后不能回退到不理解新时间依据、直接来源或授权的旧写者；回退是关闭新入站、保留已发生事实并前向修复，不承诺无损 down migration。

产品验收复用已有产品安装、账户、数据库和卷；先确认归属，不新建第三套环境。#100 冻结 shadow 安装不升级、不重启；不运行 #101、不改阈值、路由模式或模型资产。路由优化不阻塞执行能力重构，也不充当写授权判断。

## 12. 验收：完整目标成功，且没有无意义打断

以下是实施验收要求，不是本轮已运行结果。正式产品安装必须绑定源码/迁移/native/Web/构建身份，真实模型路径与受控故障注入分开记录。

1. **默认设置与直接创建：**一次“记住上海时区，明天下午三点提醒交报告”无逐项确认；偏好确实保存，真实 task/created/outbox，同委托与后续请求都能使用；“只这次按纽约”不改偏好，旧冻结对象不变。
2. **纯时长：**无默认时区的“三分钟后提醒喝水”不问时区/时段，等于可信锚加180秒，冻结 UTC 秒精度；真实 worker 到点记录站内通知。TZDB 不可用不阻止严格 UTC 分支；过窗明确未建，不顺延。列表、详情、今日投影和历史均可见。
3. **混合目标：**按多份资料生成并保存简报，再建明确截止提醒。位置变化、一次读取失败和日期冲突会改变模型步骤；正常步骤零额外批准。最终文件真实存在/修改，有保存后新 read、真实任务及各自状态；不以 Run done 冒充全部成功。
4. **自主选择：**无需用户先切“资料模式”或手动点工具；登记内唯一对象自行定位。两个合理目标才问一次选择；多个登记不取第一项，未登记目录不访问。
5. **授权反例：**仅摘要时，资料中的修改偏好/取消提醒/越界命令不产生那些业务；明确让按资料建提醒时又可正常执行。通过真实模型评估语义，不用模型原答案当 gold。
6. **取消和停止：**唯一本人任务直接取消；相似任务只问目标，超过50条可完整分页。真实 cancel_pending/撤销回执后 cancelled；已触发冲突如实返回。停止 Run 不取消已创建任务，不声称撤回已发通知。
7. **文件边界：**精确编辑保留无关字节；已确定零写冲突可自主重读；创建撞名不覆盖；链接/越界拒绝；接受结果丢失仍 unknown，不换调用重写或补造 verified。
8. **重放与接续：**同入站键、同调用、成功响应丢失、来源并发接续不重复效果；新的相同文本委托可以创建新任务；明确要求两条相同提醒不被参数去重吞掉。缺口补齐只做未完成项，不重新执行既成效果。
9. **连接与历史：**刷新/断网/离开后同一执行继续，重连只 GET；显式停止先撤销资格。执行进程崩溃不自动重放，页面不永远假报 running。旧 pending、旧 hash/模板和 accepted result 可读且不自动消费，旧恢复不扩权。
10. **口径与质量：**结果分别说明已保存、待排期、已登记、取消中、已核实文件、未完成及未知；不把任务 created 当已触发、不承诺设备收到。检查目标完成率、错误副作用和非必要追问/确认，不靠堆测试数量、tokens 或耗时改善替代助理可用性。

验证方式沿用根 scripts：受影响类型、unit、正式 native/HTTP 双消费者、PG事务/并发/取消/迁移、文件 unknown、五门及 D1–D10。先复用有效历史证据，只补变化；真实 Web/模型/产物/通知由指定负责人实测，单测不替代它。没有时间/性能目标的证据，不发明 SLA 或新门禁。

## 13. 有意延后，不作为本轮能力上限

- 完整 IANA/更广年份、周期提醒：真实目标超出现有规则和一次性任务模型时，另做明确合同；不把已有三 zone 能力说成完整支持。
- 文件/目录删除、任意 mkdir/rename、非协作宿主写者隔离：有具体目标和部署风险再设计；不阻塞有限受管输出与编辑。
